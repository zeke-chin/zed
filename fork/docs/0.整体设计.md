# 0. 整体设计

> 本仓库是 [zed-industries/zed](https://github.com/zed-industries/zed) 的**个人 fork**，不是官方 Zed。
> 它在官方代码之上增加了几项官方插件系统做不到的功能，仅供个人使用。
> `fork/` 目录下的所有内容都是 fork 自己的，官方仓库里没有这个目录。

## 1. 为什么要 fork

要加的功能都需要编辑器内部的权限，Zed 的插件接口（`crates/extension_api`）给不了：

| 功能 | 需要的能力 | 插件接口是否提供 |
|---|---|---|
| Windsurf（现 Devin）代码补全 | 注册编辑预测 provider、显示灰色预测文本、跳转 | 否 |
| Copy Anchor（复制时带路径和行号） | 接管复制、写剪贴板、状态栏 | 否 |
| JSON Explorer（JSON 识别、转换、Hover 预览） | 监听编辑、改写 buffer、切换语言、自定义 Hover | 否 |

后两项来自 VS Code 扩展 [context-kit](https://github.com/zeke-chin/context-kit)，源码在 `/Users/zeke/workspace/github_work/context-kit`。

## 2. 设计目标

1. **加新功能方便**：新功能等于新增一个 crate，再在总入口注册一行。
2. **跟进上游方便**：对上游文件的改动控制在十几行以内，全部是「挂钩行」，变基时几乎不冲突。
3. **可以整体关掉**：每个功能有独立开关，全部关闭后行为与官方 Zed 一致。

## 3. Fork 的 git 结构

阶段 1 已调整为：

| 远程 | 指向 | 用途 |
|---|---|---|
| `upstream` | `zed-industries/zed` | 只拉取，不推送 |
| `origin` | `zeke-chin/zed`（GitHub 上的 fork，已存在） | 推送自己的分支 |

| 分支 | 内容 |
|---|---|
| `main` | 上游 `main` 的镜像，不提交任何自己的改动 |
| `fork` | 日常使用和开发的分支，等于「某个上游稳定版 tag + 自己的提交」 |

`fork` 分支目前基于上游 `main`（`053d91cb14`）开发。功能开发完、第一次跟进上游时再改为基于**稳定版 tag**（形如 `v1.30.x`）变基，之后不追 `main`。稳定版大约每周一次，可以隔几个版本再跟。

改为基于 tag 时要加挂钩 H10：tag 上的 `crates/zed/RELEASE_CHANNEL` 是 `stable` 或 `preview`，必须改成 `dev`，否则编出来的应用和官方 `Zed.app` 共用应用标识和数据目录，还会检查更新。

`fork` 分支上的提交分两类，分开提交，方便变基时定位冲突：

- `fork(hook): …`：改动上游文件的提交，数量少，每个都很小。
- `fork(<功能名>): …`：只改 `fork/` 目录和自有 crate 的提交，变基时不会冲突。

> 容器内和宿主机看到的是同一个 git 仓库（`.git` 是指向 `~/.cc-runtime/git/…` 的链接），git 命令在两边都能用。GitHub 接口操作用容器内的 `gh`。
>
> 并行开发用 git worktree，统一放在仓库内的 `.agents/worktree/<名称>`，分支名 `wt/<名称>`，从 `fork` 拉出，完成后变基回 `fork`。`.agents/` 写在 `.git/info/exclude` 里，不改上游的 `.gitignore`。

```
  fork_copy_anchor/        # Copy Anchor
```

自有 crate 一律以 `fork_` 开头，和上游 crate 区分开。依赖方向是单向的：

```
zed (main.rs) ──▶ fork_ext ──▶ fork_copy_anchor
```

功能 crate 之间互不依赖。上游 crate 中只有 `zed` 依赖 `fork_ext`。

### 5.1 为什么 H4 用挂钩，不加枚举变体

接入编辑预测 provider 有两种方式，我选第二种：

| 方式 | 做法 | 冲突面 |
|---|---|---|
| A. 加枚举变体 | 在 `EditPredictionProvider` 里加 `External` | 要改 4 个文件里约 6 处穷尽匹配，包括上游改动最频繁的 `edit_prediction.rs` 和 `edit_prediction_button.rs` |
| **B. 注册表挂钩** | 官方设置写 `"provider": "none"`，fork 自己的设置决定用哪家；挂钩在官方分配 provider 之前把 fork 的 delegate 装上 | 1 个文件约 4 行 |

方式 B 的代价：官方状态栏里的编辑预测按钮在 `provider` 为 `none` 时隐藏，fork 需要自己提供一个状态栏项来显示状态和开关。

方式 B 可行的依据：`editor` crate 里没有按 `provider` 设置拦截预测的逻辑，唯一一处引用（`editor.rs:10850`）只用于遥测。如果上游以后加了这种拦截，退回方式 A。

挂钩的形状：

```rust
// FORK: 让 fork 的编辑预测 provider 优先于官方设置
if fork_ext::assign_edit_prediction_provider(editor, trigger, window, cx) {
    return;
}
```

fork 自己的设置变化时，`fork_ext` 用自己维护的编辑器列表重新分配，不依赖官方注册表。

### 5.2 为什么需要 H5 和 H6

Zed 的设置必须从中心结构 `SettingsContent` 读取（`Settings::from_settings(content: &SettingsContent)`），自有 crate 没法注册一个独立的顶层键。所以要在 `SettingsContent` 里加一个字段。

设置结构放在新文件 `crates/settings_content/src/fork.rs`，新文件不会和上游冲突。默认值写在 `fork_ext` 的 `from_settings` 里（字段缺失时取默认），不改 `assets/settings/default.json`。

### 5.3 为什么需要 H7

JSON Explorer 的悬浮窗里要有可点击的「Open value in side panel」链接。Zed 悬浮窗里所有链接的点击都经过 `open_markdown_url` 这一个函数，默认只会打开文件或网址，没有让外部 crate 处理点击的接口。

`editor` 不能反过来依赖 `fork_` crate，所以挂钩做成一个全局的处理函数槽：

```rust
// FORK: global slot for fork features to handle their `zed-fork://` links (fork/HOOKS.md H7)
pub struct ForkHoverLinkHandler(pub fn(&str, &mut Window, &mut App) -> bool);
impl gpui::Global for ForkHoverLinkHandler {}

// open_markdown_url 开头：
if link.starts_with("zed-fork://")
    && let Some(handler) = cx
        .try_global::<ForkHoverLinkHandler>()
        .map(|handler| handler.0)
    && handler(&link, window, cx)
{
    return;
}
```

槽里放函数指针而不是 `Box<dyn Fn>`：调用时要把 `&mut App` 传进去，先把指针复制出来才能结束对全局的借用。处理函数不需要捕获状态，各功能的状态放在自己的全局里。

`fork_ext::init` 注册处理函数，按链接 host 分发给各功能（`zed-fork://json-explorer/...` 交给 `fork_json_explorer::handle_hover_link`），不认识的链接返回 `false`，继续走原逻辑。工作区从链接令牌记录的编辑器取，所以签名里不需要 `Workspace`。以后别的功能要在悬浮窗里放按钮，也走这个挂钩，不用再加新的。

已核对：悬浮窗 `InfoPopover` 的链接点击经 `MarkdownElement::on_url_click` 调到 `open_markdown_url`；补全文档（`code_context_menus.rs`）、签名帮助（`signature_help.rs`）、诊断渲染器的链接也调这个函数，挂钩只拦截 `zed-fork://`，对它们没有影响。诊断悬浮窗的链接走 `DiagnosticRenderer::open_link`，不经过这里。

## 6. 功能接入框架（`fork_ext`）

`fork_ext::init` 做四件事：

1. 调用各功能 crate 的 `init`。
2. 用 `cx.observe_new::<Editor>` 给每个完整编辑器挂载各功能，并维护一份弱引用列表。
3. 用 `cx.observe_new::<Workspace>` 给每个工作区添加状态栏项。

设置类型用 `#[derive(RegisterSetting)]` 注册（通过 inventory 自动收集，不需要在 init 里手动注册）。`fork_ext` 只有 `ForkSettings`（`edit_prediction_provider`），各功能的设置类型放在各自的 crate 里（`CopyAnchorSettings`、`JsonExplorerSettings`、`WindsurfSettings`），因为功能 crate 不依赖 `fork_ext`。

默认键位不在 init 里加载，而是由挂钩 H8 调用 `fork_ext::load_default_keymap`，见 6.1。

各功能的 `attach_editor` 总是调用，功能自己在运行时检查 `enabled`，这样改开关不用重启。

每个功能 crate 对外只暴露固定的几个入口，`fork_ext` 按开关调用：

```rust
pub fn init(cx: &mut App);                                              // 注册动作
pub fn attach_editor(editor: &mut Editor, window: &mut Window, cx: &mut Context<Editor>);
pub fn status_items(workspace: &mut Workspace, window: &mut Window, cx: &mut Context<Workspace>);
```

用到的上游公开接口（都已在源码中确认存在）：

| 需求 | 接口 |
|---|---|
| 接管或新增编辑器动作 | `Editor::register_action` |
| 给键位加生效条件 | `Addon::extend_key_context` + `Editor::register_addon` |
| 自定义 Hover | `Editor::set_semantics_provider`（包一层装饰器） |
| 编辑预测 | `Editor::set_edit_prediction_provider` + `EditPredictionDelegate` |
| 状态栏 | `StatusItemView` + `StatusBar::add_left_item` / `add_right_item` |
| 加载键位 | `KeymapFile::load` |
| 切换语言 | `Buffer::set_language` |

### 6.1 键位策略

fork 的功能一律定义**自己的动作**，再用键位绑定触发，不覆盖上游动作的实现。例如 Copy Anchor 定义 `copy_anchor::Copy`，在 `Editor && copy_anchor_enabled && selection` 上下文里绑定 `cmd-c`。

键位文件 `fork/keymaps/default-macos.json` 编译期内嵌。Zed 每次重新加载键位（用户改 `keymap.json`、切换 base keymap、开关 Vim 模式）都会先 `clear_key_bindings()`，再调用 `load_default_keymap` 和绑定用户键位。所以 fork 的键位挂在 `load_default_keymap` 末尾（H8）：每次重新加载都会绑定，排在官方默认键位之后、用户键位之前，来源标为 `KeybindSource::Default`。用户键位能覆盖 fork 键位，fork 键位能覆盖官方默认键位。

这样做的好处：功能关闭后上下文条件不成立，按键自动回到官方行为；菜单里的「复制」始终是原生复制，和 VS Code 版一致；用户可以在自己的 `keymap.json` 里改键。

## 8. 各功能的设计要点

### 8.1 Windsurf 编辑预测

官方 IDE 的补全链路是「编辑器 → 本地 Language Server（下称 LS，一个闭源的 Go 程序）→ 云端」。**首选方案是用 Rust 重写 LS 的职责，直连云端，不经过官方 LS**；调用官方 LS 只作为备选：

```
首选：编辑器 ──▶ WindsurfDelegate ──▶ 上下文采集 ──▶ NativeBackend ──HTTPS──▶ Windsurf 云端 GetTab
备选：编辑器 ──▶ WindsurfDelegate ──▶ 上下文采集 ──▶ LanguageServerBackend ──HTTP──▶ 本地官方 LS ──▶ 云端
```

#### 目标：最新接口、最全上下文、原生实现

- **最新接口**：只做 Tab（下一处编辑 + 跳转），对应云端的 `ApiServerService/GetTab`。旧的经典补全 `GetCompletions` 不做。
- **最全上下文**：官方客户端发给云端的每一类上下文都要提供，见下表。
- **原生实现**：官方 LS 的职责（采集上下文、维护编辑轨迹、调云端、解析流式结果）全部用 Rust 在 Zed 进程内实现。省掉一个常驻进程和一次本地转发，上下文也能直接从 Zed 内存里取。
- **备选**：协议验证后如果原生方案走不通，退回到调用官方 LS 二进制（`8.Windsurf备选-LS桥接.md`）。

#### 原生方案可行的依据

根据逆向仓库提取的 proto（`jaredboynton/modelgate`，2026 年 6 月的版本），云端 `GetTab` 的请求是结构化的上下文组件，不是拼好的提示词：

```proto
GetTabRequest {
  Metadata metadata;                              // 凭据、客户端标识
  UnifiedPromptComponents unified_prompt_components; // 上下文组件
  TabTrajectoryStepsV2 trajectory_steps_v2;       // 用户操作轨迹（带哈希去重）
  Language language; Model model; ExperimentConfig experiment_config; ...
}
```

响应是流式的 `DeltaTab`，三选一：`DeltaSupercomplete`（改哪几行、旧文本、新文本、光标位置）、`DeltaTabJump`（跳到哪）、`DeltaNoop`。响应的第一条 `PreResponse` 里带服务端拼好的提示词，说明**提示词由服务端组装**，客户端只需要把上下文组件填对。

这份 proto 有几个月了，字段可能已经变化；轨迹哈希怎么算、`experiment_config` 填什么、凭据要不要先换成短期令牌，都没验证过。这些是阶段 2 要回答的问题。

#### 上下文清单

| 上下文 | proto 字段 | 在 Zed 里的来源 |
|---|---|---|
| 当前文档、光标、可见范围、选区 | 轨迹里的 `supercomplete_active_doc` 步骤 | 当前 buffer 快照、编辑器滚动位置 |
| 编辑历史 | `trajectory_steps_v2` 里的编辑类步骤 | 订阅 buffer 编辑事件，自己维护轨迹 |
| 浏览过的文件和代码片段 | 轨迹里的 `view_file`、`view_code_item` 步骤 | 订阅工作区活动项变化、光标停留 |
| 诊断 | `code_diagnostics` | buffer 快照的诊断 |
| 其他打开的文件 | `other_documents` | ~~工作区里打开的 buffer~~ 阶段 2 实测官方 LS 不发，不做 |
| 检索到的相关代码 | `context_module_result` | ~~自己实现检索~~ 阶段 2 实测官方 LS 不发，不做 |
| 剪贴板 | 轨迹里的 `clipboard` 步骤 | 系统剪贴板 |
| 上次预测的接受和拒绝 | `supercomplete_feedback_context` 及对应的反馈步骤 | delegate 的 `accept` / `discard` |
| 终端输出 | 轨迹里的 `read_terminal` 步骤 | Zed 终端面板，是否采用看官方客户端发不发 |
| 官方 agent 的对话历史 | `cortex_trajectory`、`chat_messages` | 不提供，Zed 里没有对应物 |

每一类上下文是一个独立的采集器，实现同一个接口，可以单独开关和测试。阶段 2 抓到官方客户端的真实请求后，以它为准核对这张表。

> 阶段 2 已核对（`fork/spike/结论.md` 第 5 节）：当前文档和光标走 `command_intent_info`，不是轨迹步骤；跳转预测不在 `GetTab` 里，而是本地拼提示词调 `GetChatMessage`；结论选择**原生方案**。

#### 结构

```
fork_windsurf/src/
  fork_windsurf.rs       # init、全局实体、对外入口
  delegate.rs            # EditPredictionDelegate 实现
  backend.rs             # TabBackend 接口；NativeBackend 与 LanguageServerBackend 两个实现
  native/                # 首选：认证、Connect 流式客户端、GetTab 请求组装、轨迹哈希缓存
  context/               # 上下文采集器，每类一个文件
  trajectory.rs          # 用户操作轨迹的记录与裁剪
  diff.rs                # DeltaTab 转成 Zed 的编辑
  proto/                 # prost 生成的消息定义，只保留用到的
  status.rs              # 状态栏项
```

- `TabBackend` 接口把「上下文 → 预测」抽象出来，delegate 和上下文采集与后端无关。两个后端可以在设置里切换（`fork.windsurf.backend`: `"native"` 或 `"language_server"`），方便对比效果。
- 写成独立的 `EditPredictionDelegate`（参考 `crates/codestral`），不接入 `EditPredictionStore`。接入 store 要改 3688 行的 `edit_prediction.rs`。
- 响应映射：`DeltaSupercomplete` 转成 `EditPrediction::Local { edits, cursor_position }`，`DeltaTabJump` 转成光标预测或 `EditPrediction::Jump`。
- 协议用工作区已有的 `prost` 编解码，HTTP 用仓库的 `http_client`，不新增网络依赖。

#### 性能预期

预测延迟的大头是网络和云端模型推理，这部分重写不会变快。原生实现能省下的是：本地转发一跳、官方 LS 的常驻内存和索引开销、上下文在两个进程间的序列化。阶段 5 会实测两个后端的延迟和内存来对比。

未验证的部分集中在协议上，见阶段 2。

#### 凭据：一个存放位置，两种写入方式

`api_key` 只存在**一个地方**：用户 `settings.json` 的 `fork.windsurf.api_key` 字段。运行时只从这里读。

写入有两种方式，结果写到同一个字段：

| 方式 | 入口 | 行为 |
|---|---|---|
| 从本机导入 | 状态栏菜单的「从本机导入密钥」按钮，或动作 `windsurf: import api key` | 去本机 Devin/Windsurf 的登录数据里找 `api_key`，找到后写入 `settings.json` |
| 手动填写 | 直接编辑 `settings.json`；状态栏菜单的「填写密钥」按钮会打开设置文件并定位到该字段 | 用户自己把值填进去 |

```
「从本机导入」按钮 ──▶ 读本机登录数据 ──┐
                                         ├──▶ settings.json 的 fork.windsurf.api_key ──▶ WindsurfClient
手动编辑设置文件 ───────────────────────┘
```

- 导入是一次性动作，只在点按钮时读一次本机登录数据。fork 不会在后台自动读，也不会定时同步。
- 导入用 Zed 的设置写入接口（`update_settings_file`）改写用户设置文件，保留文件里原有的注释和格式。
- 导入成功时提示找到的来源和打码后的密钥；找不到时提示原因，并引导改用手动填写。
- 字段里已有值时，导入会先确认再覆盖。
- 设置文件变化后即时生效，不需要重启。
- 字段为空时不发任何请求，状态栏显示「未配置密钥」，点击后给出上面两个按钮。
- 如果云端要求先把 `api_key` 换成短期令牌，换取和刷新由客户端在内存里完成，短期令牌不落盘。
- 密钥失效（服务端返回认证错误）时，状态栏提示重新导入或重新填写。
- 只认用户级设置。项目级 `.zed/settings.json` 里的 `api_key` 会被忽略，避免密钥被提交进项目仓库。
- 密钥在 `settings.json` 里是**明文**。把这个文件放进 dotfiles 仓库、截图或分享给别人之前，要先去掉这个字段。选这个方案是为了自己查看和修改方便，没有用 Zed 存其他密钥的钥匙串方式。
- 阶段 2 的验证脚本是同样的结构，见 `2.Windsurf协议验证.md`。

### 8.2 Copy Anchor

- `core`：纯函数，生成带路径行号的代码块、修剪首尾空行、围栏保护、预览截断。从 TypeScript 直接移植，测试用例一并移植。
- 动作：`copy_anchor::Copy`、`copy_anchor::ToggleContextMode`。
- 状态：全局实体保存上次复制的「原文」和「带锚点文本」，用于切换模式时改写剪贴板。
- 状态栏：右侧模式标识（可点击切换），左侧复制预览（定时消失）。

### 8.3 JSON Explorer

- `core`：JSON 判断、Python repr 解析、字符串内换行修复、Markdown 识别。约 900 行 TypeScript，移植到 Rust，基于 `serde_json`。
- 粘贴识别：订阅 buffer 编辑事件，Plain Text buffer 被整体替换时检测内容。
- 转换命令：`json_explorer::ToggleCurrentDocument`，默认 `cmd-;`。
- Hover 悬浮窗：包装 `SemanticsProvider`，JSON 文件里鼠标悬停在字符串值上时弹出预览，包含标题、键路径、预览内容，以及顶部和底部各一个可点击的「Open value in side panel」链接。链接点击通过挂钩 H7 处理，效果与 VS Code 版一致。
- 解析嵌套值：动作 `json_explorer::ParseNestedValue`，在右侧分栏打开解析后的新文档。悬浮窗链接、键位、命令面板三个入口都调用它。

和 VS Code 版的差异：没有字符串值上方的行内 CodeLens 按钮。Zed 的 CodeLens 绑死在 LSP 上（`code_lens.rs`），不走这条路，入口由悬浮窗链接和键位代替。

## 9. 构建与发布

- 仓库 `crates/zed/RELEASE_CHANNEL` 是 `dev`，自己编译出来的是 **Zed Dev**。Dev 通道不检查更新（`ReleaseChannel::poll_for_updates`），不会被官方版覆盖。
- Zed Dev 和官方 `Zed.app` 的应用标识、数据目录都分开，可以并存。官方版留作对照和回退。
- 日常开发用 `cargo run`，自用版本用 `script/bundle-mac` 打包。
- 分工：代码在容器里改；编译、`cargo check`、`./script/clippy`、测试、运行都在宿主机上通过 ssh 执行。
- 宿主机的 `~/.cargo/config.toml` 把 `build-dir` 设成 `~/workspace/rust_work/.cache/{workspace-path-hash}`，每个 worktree 路径不同，默认会各自冷编译。worktree 里编译时设 `CARGO_BUILD_BUILD_DIR=/Users/zeke/workspace/rust_work/.cache/0d/83a59d3332740c`（主仓库的缓存目录），复用已编译的依赖。代价是同一时间只能有一个 cargo 在编译，其他的排队等锁。
- 宿主机环境：16 核、64 GB、Xcode 27.2、已装 rustup，工具链由 `rust-toolchain.toml` 固定为 1.98.1。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 云端 `GetTab` 无法由自写客户端调通（轨迹哈希、实验配置、令牌换取等有未知校验） | 原生方案不可行 | 阶段 2 先在 Zed 之外验证；不通过就改做备选的 LS 桥接 |
| 自己实现的上下文采集与官方 LS 有差距 | 预测质量不如官方 | 以抓到的官方请求为基准逐类对齐；保留 LS 后端做并排对比 |
| 直连云端的请求与官方客户端有可识别的差异 | 封号风险比调用官方 LS 更高 | 请求字段、请求头、频率都对齐官方客户端；凭据只在用户主动导入或填写时写入；只用自己的账号 |
| 云端协议升级 | 预测失效，且没有官方 LS 兜底适配 | proto 集中在一个模块；失败时自动切到 LS 后端或降级为无预测，并在状态栏提示；保留从新版 LS 重新提取 proto 的脚本 |
| `api_key` 明文存在 `settings.json` | 配置文件外传时密钥泄露 | 只认用户级设置；日志和提示里一律打码；文档里写明注意事项 |
| 上游重构挂钩点附近的代码 | 变基冲突 | 挂钩行少且有标记，按 `HOOKS.md` 逐条重放 |
| 上游改动 fork 用到的公开接口 | 编译失败 | 编译器会报出来；适配代码都在 `fork_` crate 内 |
