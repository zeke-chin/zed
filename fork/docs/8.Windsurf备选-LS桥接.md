# 8. Windsurf 备选方案：LS 桥接

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。
>
> **已实现**（`crates/fork_windsurf/src/language_server.rs` 及 `language_server/`），作为原生方案出问题时的备用后端，实现细节见文末「实现记录」。
>
> 阶段 2 结论是走原生方案，本阶段原计划暂不做。补充两点（见 `fork/spike/结论.md` 问题 6–9、验收 7）：LS 要先收到 `RefreshContextForIdeAction`（STARTUP、ACTIVE_EDITOR_CHANGED、500 ms 防抖的 SELECTION_CHANGED）才开始记录编辑；云端报错时 LS 对 `HandleStreamingTabV2` 不响应，桥接要自己设超时。参照 `fork/spike/lib/ls_driver.py`。

## 定位

这是**退而求其次的方案**：不自己实现客户端，而是在本机拉起官方的 Language Server（LS）二进制，把上下文交给它，由它去调云端。

只在下面两种情况下做：

- 阶段 2 的结论是原生方案（直连云端）不可行。
- 原生方案已经完成，需要一个官方实现做并排对比，或者在云端协议升级后临时兜底。

## 与原生方案的对比

| | 原生方案（阶段 4、5） | LS 桥接 |
|---|---|---|
| 上下文采集、轨迹、检索 | 自己用 Rust 实现 | 官方 LS 完成，质量与官方一致 |
| 常驻进程 | 无 | 一个 LS 进程，有自己的索引和内存开销 |
| 链路 | Zed → 云端 | Zed → 本地 LS → 云端 |
| 协议升级 | 要自己跟进 | 换新版 LS 二进制即可，本地接口变化较少 |
| 依赖 | 无 | 需要本机有官方 LS 二进制 |
| 与官方客户端的差异 | 请求由自己构造 | 发往云端的请求由官方 LS 构造 |

## 复用的部分

`WindsurfDelegate`、状态栏、凭据、`diff.rs`、上下文采集器框架都与后端无关。本阶段只新增 `TabBackend` 的另一个实现 `LanguageServerBackend`，用设置 `fork.windsurf.backend` 切换。

如果是因为原生方案不可行才做本阶段，阶段 4 里与后端无关的部分（4.2 凭据、4.5 响应转编辑、4.6 Delegate、4.7 接入与状态栏）要在本阶段一并实现。

## 要做的事

### 8.1 LS 进程管理

- 定位二进制：先取设置 `fork.windsurf.language_server_path`，为空时在本机已装的 Devin/Windsurf 里找。不自动下载。
- 惰性启动：第一次需要预测时才启动；整个应用进程只启动一个，所有窗口共用。
- 启动参数、取端口的方式、心跳，按阶段 2 的最小验证结果。
- 退出清理：Zed 退出时结束 LS，不留孤儿进程。
- 崩溃恢复：LS 意外退出后，下一次请求时重启；连续失败时退避，最长间隔 1 分钟。
- 进程启动使用仓库现有的 `util::command` 封装。

### 8.2 请求

调用本地接口 `LanguageServerService/HandleStreamingTabV2`。IDE 侧要提供的原始上下文比云端请求简单：

| 字段 | 来源 |
|---|---|
| `document` | 当前 buffer 全文、光标、语言、路径、工作区根目录 |
| `other_documents` | 其他打开的 buffer |
| `diagnostics` | buffer 诊断 |
| `clipboard_entry` | 系统剪贴板 |
| `intellisense_suggestions` | 补全菜单候选，拿不到就不填 |
| `disable_tab_jump` | 设置 `fork.windsurf.tab_jump` 取反 |

这些字段直接复用阶段 4、5 的上下文采集器。

LS 自己维护编辑轨迹和索引，所以还要按阶段 2 抓到的 IDE → LS 流量，补上 IDE 平时会发的状态同步调用（例如文档打开、内容变化、工作区初始化）。缺了这些，LS 的轨迹和检索是空的，预测质量会下降。

### 8.3 响应

`HandleStreamingTabV2Response` 是三选一：`Diff`、`TabJump`、`NoOp`。转换成与原生后端相同的内部结果类型，后面复用 `diff.rs` 和 delegate。

### 8.4 反馈上报

按 IDE → LS 流量里的做法，上报接受和拒绝。

### 8.5 状态栏

LS 后端启用时，状态栏菜单多两项：重启 LS、显示 LS 版本和路径。找不到二进制时显示「未找到 Language Server」并提示配置路径。

## 待确认事项

结论（阶段 8 实现时确认）：

- **一个 LS 能否服务多工作区**：能。整个 Zed 进程只起一个 LS，LSP `initialize` 带上当时已知的全部工作区，之后新出现的工作区（新窗口、新 worktree）用 `workspace/didChangeWorkspaceFolders` 补上（LS 的 `initialize` 回复里声明了 `workspaceFolders.changeNotifications`）。每次请求、`RefreshContextForIdeAction` 都带全部 `workspace_uris`，文档用绝对 `file://` URI，不依赖 LS 的工作目录（LS 的 cwd 设为它的数据目录）。
- **远程项目**：禁用。文件不在本机的 buffer 不同步给 LS、不发请求，状态栏显示「Windsurf: not in remote projects」，提示改用原生后端。
- **索引的内存和磁盘**：有参数。`--enable_index_service` 默认是 `true`，桥接传 `--enable_index_service=false`，也不传 `--enable_local_search`（Tab 不用检索结果，`fork/spike/结论.md` 问题 13）。实测小工作区：LS 启动后空闲约 147 MB RSS，三次请求后约 282 MB；数据目录只有几个小文件（`codeium/code_tracker` 等），`database/` 为空。索引开着时小工作区空闲 RSS 也是 130–140 MB 量级（阶段 2 脚本实测），差别要在大仓库上才明显。其余可调的：`--limit_go_max_procs`（默认 4）、`--indexed_files_retention_period_days`、`--file_watch_max_dir_count`，桥接都用默认值。

## 不做的事

- 不自动下载或更新 LS 二进制。
- 不做旧的经典补全 `GetCompletions`。

## 实现记录（阶段 8）

### 结构

| 文件 | 内容 |
|---|---|
| `language_server.rs` | `LanguageServerBackend`：实现 `TabBackend`；进程生命周期（惰性启动、共享一次启动、崩溃重启、退避）、文档同步、心跳、反馈。不依赖 gpui，计时器 / 时钟 / 任务派发都是注入的 |
| `language_server/binary.rs` | 找二进制、读所在 app 的 `product.json`（`windsurfVersion`、`codeiumVersion`） |
| `language_server/process.rs` | 真正拉起 LS：假扩展服务（tiny_http）、父进程管道（Unix socket）、stdin 元数据、日志 |
| `language_server/http.rs` | 到 LS 本地端口的 Connect 一元调用（自写的最小 HTTP/1.1 客户端） |
| `language_server/lsp.rs` | LSP over TCP（读写各一个线程，发通知不阻塞主线程） |
| `language_server/request.rs` | 请求组装、响应转 `TabStream`、`didChange` 增量计算 |
| `language_server/tests.rs` | 传输层对假 TCP 服务的测试、后端对内存假 LS 的测试、delegate 端到端测试、`#[ignore]` 的真实 LS 测试 |

`Windsurf` 全局状态里原生后端一直在；`fork.windsurf.backend` 为 `"language_server"`（且已启用、有密钥）时额外创建 `LanguageServerBackend`，请求改走它。设置变化时切换，不用重启 Zed。

### 二进制与启动

- 查找顺序：设置 `fork.windsurf.language_server_path`（支持 `~/`）→ `/Applications/{Devin,Windsurf}.app/Contents/Resources/app/extensions/windsurf/bin/language_server_macos_{arm,x64}` → `~/Applications/` 下同样的路径 → `~/.codeium/windsurf/bin/language_server_*`；Linux 查 `/usr/share/{devin,windsurf}`、`/opt/{Devin,Windsurf}`。配置了路径但文件不存在时直接报错，不回退到自动查找。
- 进程用 `util::command::new_command` 起，`kill_on_drop`。参数（与 `ls_driver.py` 一致，除了索引和数据目录）：`--api_server_url https://server.codeium.com --run_child --enable_lsp --extension_server_port <假扩展服务端口> --ide_name windsurf --random_port --inference_api_server_url https://inference.codeium.com --database_dir <数据目录>/database --enable_index_service=false --codeium_dir <数据目录>/codeium --parent_pipe_path <socket> --windsurf_version <product.json 的 windsurfVersion> --stdin_initial_metadata --detect_proxy=false`。
- 环境变量：`WINDSURF_CSRF_TOKEN`（每次启动一个 uuid）、`CODEIUM_EDITOR_APP_ROOT`（二进制所在 app 的 `app` 目录）；Zed 设置了 `proxy` 时再加 `HTTPS_PROXY`/`HTTP_PROXY`（`NO_PROXY=127.0.0.1,localhost`）。
- **api_key**：编码成 `Metadata` 写进 stdin 后关闭（`--stdin_initial_metadata`），之后每个请求的 `metadata.api_key` 也带上。密钥或二进制路径变化时停掉 LS，下次请求用新值重启。
- **端口与 csrf**：LS 起来后调假扩展服务的 `LanguageServerStarted`，带 Connect 端口、LSP 端口和 csrf token。假扩展服务只接受带我们 csrf 头的调用（端口是带密钥的请求要去的地方，不能让别的本地进程冒充），其余方法（`GetNativeValues`、`SetNativeValue` 等）回空。60 秒内没回报、或者进程中途退出，算启动失败，错误信息里带 LS 输出的最后几行。
- 拿到端口后连 LSP：`initialize`（`clientInfo` 为 Devin + 版本，带工作区）→ `initialized`，`serverInfo.version` 是构建号（如 `fcf7ba39…`），用作「版本」的一部分。然后发 `RefreshContextForIdeAction(STARTUP)`，再对所有已跟踪的文档发 `didOpen`。
- **数据目录**：`paths::data_dir()/windsurf-ls`（macOS 上是 `~/Library/Application Support/Zed/windsurf-ls`），下有 `database/`、`codeium/`、`language_server.log`（每次启动截断，上限 5 MB）。LS 有 `--codeium_dir`、`--database_dir` 两个参数可以完全避开 `~/.codeium`；真实测试里 `lsof` 确认 LS 没有打开 `~/.codeium` 下的任何文件。
- 只在 Unix 上实现（父进程管道用 Unix socket）；Windows 上选 LS 后端会报启动失败。

### 状态同步调用清单

| 时机 | 调用 |
|---|---|
| 启动后 | LSP `initialize` / `initialized`；Connect `RefreshContextForIdeAction{ide_action: STARTUP, workspace_uris}`；对所有已跟踪文档 LSP `textDocument/didOpen`（全文） |
| buffer 编辑 / 重新加载 | LSP `textDocument/didChange`，增量（UTF-16 位置，算法与 `lsp_store` 的增量同步相同），版本号递增 |
| buffer 释放 | LSP `textDocument/didClose` |
| 出现新工作区 | LSP `workspace/didChangeWorkspaceFolders` |
| 请求的文档和上次不同 | 先 `RefreshContextForIdeAction{ACTIVE_EDITOR_CHANGED, active_document, other_documents, workspace_uris, recently_opened_uris}`，再发请求 |
| 光标移动 | `RefreshContextForIdeAction{SELECTION_CHANGED}`，500 ms leading 防抖（delegate 的 `suggest` 在每次选区变化时被调用，挂在那里） |
| 每次触发 | `HandleStreamingTabV2`（见下） |
| 接受 / 拒绝 / 跳转落地 | `ProvideCompletionFeedback` |
| 每秒 | `Heartbeat`；连续 3 次失败视为 LS 已死 |
| 停止 | `Exit`（最多等 500 ms，退出 Zed 时 150 ms），然后按 pid 结束自己起的进程 |

没有发的：`VISIBLE_RANGES_CHANGED`、`SAVE`（`extension.js` 会发，阶段 2 抓包里对 Tab 没有影响，Zed 也没有现成的事件可挂）。

### 请求

- `HandleStreamingTabV2Request`：`metadata`（官方扩展的取值，`ide_version`/`extension_version`/`extension_path` 换成二进制所在 app 的）、`document`（全文、UTF-8 字节 `cursor_offset`、`editor_language`、`line_ending`、`is_dirty`、`timestamp`，不填 `language` 和 `cursor_position`，与 `getDocumentInfo` 一致）、`editor_options`（语言设置的 `tab_size` / `hard_tabs`）、`diagnostics`（复用光标 ±10 行、前 5 条）、`clipboard_entry`（5 秒内复制的，沿用原生的过滤）、`other_documents`（其他已跟踪的本地 buffer，总量 1 MiB）、`disable_tab_jump = !fork.windsurf.tab_jump`、`supercomplete_trigger_condition`（Zed 的触发映射：编辑→`TYPING`、显式→`FORCED`、接受预测→`SUPERCOMPLETE_ACCEPT`、接受 LSP 补全→`AUTOCOMPLETE_ACCEPT`、其他→`CURSOR_LINE_NAVIGATION`，跳转落地→`TAB_JUMP_ACCEPT`）。`intellisense_suggestions` 不填（拿不到补全菜单）。
- 超时 12 秒（LS 自己对云端是 9.3 秒；云端报错时 LS 根本不回）。超时算网络错误，走原有的退避。
- LS 启动后还没收到过 `didChange` 时不发请求，直接当作「无预测」：这时 LS 发给云端的是空轨迹，云端报错、LS 不响应，只会白等 12 秒。实际效果是 LS（重）启动后要再输入一下才出预测。

### 响应

- `Diff`：替换的是请求文档里 `[selection_start_line, selection_end_line)` 这几整行（`extension.js` 的 `computeFinalDocumentState`）。`character_diff` 里「未变 + 删除」拼成旧文本、「未变 + 插入」拼成新文本，`TabStream` 多带 `line_range`，delegate 用这几行在请求时快照里的字节范围代替原生的选区窗口，后面照旧走 `diff.rs`、缓冲区变化检查和预览。路径是 `file://` URI，转成绝对路径再比较。
- `TabJump`：只有位置（行 0 起，列按 UTF-16，见下）。显示为 `EditPrediction::Jump`（编辑器里是「Jump to <文件>」），同文件也一样；目标在别的文件时用 project 打开。光标到达目标位置时（在 `suggest` 里检测，因为编辑器移动光标后只调 `suggest` 不调 `refresh`）发 `TAB_JUMP_ACCEPT` 请求拿那里的修改，并上报接受。
- `NoOp`、带 `filter_reason` 的回复：无预测（`filter_reason` 记在 show last request 里）。
- **列单位**：`extension.js` 把 `jump_position` 直接传给 VS Code 的 `Position`，所以按 UTF-16 处理，超出行尾时截断到行尾。没用多字节样本在真实 LS 上核实过。`Diff.cursor_position` 不用（光标放在最后一处修改的末尾，与原生一致）。
- 原生专属逻辑在 LS 后端下关掉：预测性预取（`prepare_predictive_request` 直接返回）、轨迹哈希缓存（不发轨迹）、原生 Tab Jump 的 `GetChatMessage`（`tab_jump::start` 返回 `None`）、`ProvideFeedback` 5 秒限频。保留的是 Zed 侧沿预测输入时的本地裁剪（不发请求），LS 自己的「typing as suggested」缓存也照常起作用。
- 本地轨迹（原生用的）照常记录，切回原生后端时历史还在。

### 反馈

`ProvideCompletionFeedback{metadata, is_accepted, feedback_delay_ms, completion_id, prompt_id, source: PROVIDER_SOURCE_SUPERCOMPLETE, document, is_intentional_reject}`，`completion_id`/`prompt_id` 用 LS 回复里的。每次接受、Esc 拒绝都发（官方扩展不限频），Tab Jump 落地算接受、被拒绝算拒绝。LS 没在运行时不发（新起的 LS 不认识旧的 completion）。

### 进程生命周期与孤儿进程防护

- 惰性启动：第一次请求才启动；并发的请求共享同一次启动，启动本身派发到后台执行，请求被取消也不会中断启动。
- 全应用一个：`LanguageServerBackend` 挂在全局 `Windsurf` 上，所有窗口共用。
- 崩溃：每次请求前检查进程（`try_status`）和 LSP 连接，心跳连续失败也算；死了就丢掉，下次请求立即重启并重新 `didOpen` 所有文档。
- 启动失败（含找不到二进制）退避 1、2、4…最长 60 秒，退避期间请求直接失败，不重复查找/启动；成功一次清零。
- 结束：切回原生、关掉 Windsurf、不再选 Windsurf 作为 provider、改密钥或路径时先发 `Exit`，再按 pid 结束（只结束自己起的子进程，不按名字）；Zed 正常退出时在 `on_app_quit` 里做同样的事（`Exit` 只等 150 ms，gpui 退出时总共等 200 ms）。
- Zed 崩溃 / 被 `kill -9`：LS 的 `--parent_pipe_path` 指向 Zed 监听的 Unix socket（`$TMPDIR/zed_windsurf_<16 位十六进制>`），LS 连上后一直保持连接；Zed 进程没了，内核关掉 socket，LS 日志里出现「Parent pipe closed」后自行退出（实测 0.2 秒）。另外实测不发心跳 90 秒 LS 也不会自己退出，所以心跳不能当作兜底，靠的是父进程管道。

### 状态栏

- 新状态：「Windsurf: starting…」（启动中）、「Windsurf: language server not found」（找不到二进制，提示设置 `language_server_path` 或改回 native）、「Windsurf: language server failed」（启动失败，带原因和重试倒计时）、「Windsurf: not in remote projects」。凭据失效沿用原有的「key rejected」：LS 对请求返回 `unauthenticated` / `permission_denied` 时映射过去（LS 实际在密钥失效时怎么回没有验证，见下）。
- 菜单在 LS 后端下多两项：「Restart Language Server」（`windsurf: restart language server`，停掉并立即重启）、「Show Language Server Version and Path」（`windsurf: show language server info`，只读 JSON：状态、二进制路径、`codeiumVersion`、app 版本、构建号、pid、数据目录、日志路径）。

### 测试

- 传输层：HTTP 客户端对假 TCP 服务（Content-Length、chunked、Connect 错误 JSON、连接被拒）；LSP 连接对假 LSP 服务（`initialize` 往返、回答 `workspace/configuration`）；用一个立即退出的脚本当二进制，检查启动失败的报错带输出。
- 后端对内存假 LS：启动、STARTUP / ACTIVE_EDITOR_CHANGED 顺序、`didOpen` / 增量 `didChange`、请求字段；超时（12 秒前不返回、之后网络错误）；错误透传；LS 进程退出后自动重启并重新打开文档（验收 8）；启动失败的退避；找不到二进制；改设置后停掉 LS。
- delegate 端到端：预测显示的编辑位置、接受后的 `ProvideCompletionFeedback`、不发预取；Tab Jump 显示、落地触发 `TAB_JUMP_ACCEPT` 和接受反馈、拒绝反馈；两个后端来回切换（切走 LS 被结束、切回下次请求重启）；状态栏文案。
- 真实 LS（`live_language_server`，`#[ignore]`）：`WINDSURF_LS_ENV=<含 WINDSURF_API_KEY 的文件> cargo test -p fork_windsurf --lib live_language_server -- --ignored --nocapture`。用临时数据目录和临时 git 工作区起本机 Devin.app 的 LS，逐字输入一行，发 3 次请求（间隔 ≥2.5 秒），检查拿到预测、`~/.codeium` 没被打开、结束后进程不在。

### 实测：延迟与内存（验收 10）

宿主机 MacBook（M3 Max），Devin.app 3.10.48 / LS 1.48.2，小工作区（一个 25 行的 Python 文件），跑了两遍真实测试（共 6 次 `HandleStreamingTabV2`）：

| | LS 桥接 | 原生 |
|---|---|---|
| 额外进程 | 1 个 LS | 无 |
| LS 启动到可用 | 约 700 ms（含 LSP initialize、STARTUP） | — |
| 内存 | LS 启动后空闲约 147 MB RSS，3 次请求后约 282 MB | 只在 Zed 进程内多一份轨迹和哈希，没有单独测（量级可忽略） |
| 第一次请求（冷） | 1295 / 757 ms | 阶段 2 实测完成 P50 559 ms / P90 707 ms（首条增量 P50 374 ms） |
| 沿预测继续输入 | 1–2 ms（LS 本地缓存命中） | 0 ms（Zed 侧本地裁剪，不发请求） |
| 输入预测不到的内容 | 334 / 341 ms | 同「第一次请求」，或命中预测性预取时 0 ms |

LS 一侧的单次延迟和阶段 2 的 `ls-diverge`（P50 682 ms）相比更低，样本太少，只能说明量级相当；原生少一跳、少一个常驻进程，LS 的优势是请求和上报由官方代码构造。

### 与正文的出入

- 正文说「复用 Tab Jump 的展示逻辑」：原生 Tab Jump 自带跳过去之后的修改，可以直接显示成远处的修改；LS 的 Tab Jump 只有位置，所以显示成 `EditPrediction::Jump`（同文件也显示「Jump to <文件名>」），落地后再请求一次拿修改，和官方扩展「Tab to Jump → TAB_JUMP_ACCEPT」的流程一致。
- 正文 8.2 说复用阶段 4、5 的上下文采集器：诊断、剪贴板、文档复用了；`intellisense_suggestions` 拿不到不填。
- 没做 `VISIBLE_RANGES_CHANGED`、`SAVE` 两种 IDE 动作。
- 索引默认关掉（正文没提）。
- 「凭据失效有提示」只能做到 LS 返回认证错误时提示；LS 在密钥失效时是回错误还是不响应没有验证（不想拿无效密钥去打云端）。如果是不响应，表现为超时（「offline」）。
