# 7. 上游同步与发布

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。

## 目标

把「跟进上游新版本」和「打出自用安装包」做成固定流程，每次同步的人工工作量控制在半小时以内（不含编译时间）。

这一阶段的脚本可以在阶段 1 之后随时做，建议在第一次需要跟进上游之前完成。

## 要做的事

### 7.1 同步脚本 `fork/sync-upstream.sh`

输入一个上游稳定版 tag，执行：

1. `git fetch upstream --tags`。
2. 把 `main` 快进到 `upstream/main`。
3. 给当前 `fork` 分支打备份标签 `fork-backup/<日期>`。
4. 把 `fork` 变基到目标 tag。
5. 变基成功后依次执行 `fork/check-hooks.sh`、`cargo check -p zed`、各 `fork_` crate 的测试。
6. 任何一步失败就停下并打印当前状态，不自动解决冲突，不自动推送。

推送 `fork` 分支需要强制推送，这一步保持手动执行。

### 7.2 冲突处理手册 `fork/HOOKS.md`

对每个挂钩写明「上游改了这里时怎么重放」：

| 挂钩 | 冲突时的处理 |
|---|---|
| H1、H2 `Cargo.toml` | 接受上游版本，重新加上 fork 的几行 |
| H3 `main.rs` | 接受上游版本，在 `edit_prediction_registry::init` 之后重新加一行 |
| H4 注册表 | 接受上游版本，在 `assign_edit_prediction_provider` 函数体开头重新加挂钩；如果函数签名变了，同步调整 `fork_ext` 里的对应函数 |
| H5 `SettingsContent` | 接受上游版本，重新加字段和 `mod` 声明 |
| H6 `fork.rs` | 新文件，不会冲突；派生宏或属性变化时按编译错误修改 |
| H7 悬浮窗链接 | 接受上游版本，在 `open_markdown_url` 函数体开头重新加挂钩；函数被改名或拆分时，找到悬浮窗 `on_url_click` 最终调用的函数，把挂钩放过去 |

### 7.3 接口适配记录

上游改了 fork 用到的公开接口时，编译会失败。每次适配在 `fork/CHANGELOG.md` 里记一行：上游版本、哪个接口变了、怎么改的。重点关注这几个接口：

- `EditPredictionDelegate` 和 `EditPrediction`
- `SemanticsProvider`（方法增减会直接影响 Hover 装饰器）
- `Editor::register_action`、`Addon`
- `StatusItemView`
- `Settings` trait 和 `SettingsContent`

### 7.4 打包

- 用 `script/bundle-mac` 打出本机架构的 Zed Dev 安装包，使用本地临时签名。
- 包装成 `fork/bundle.sh`，产物放到固定目录，文件名带上游版本号和 fork 提交号。
- 应用的「关于」信息里能看出这是 fork 构建（例如版本字符串带 `fork` 后缀）。实现方式优先用构建时的环境变量，不改上游代码；做不到就保持原样。

### 7.5 回归清单 `fork/回归清单.md`

每次同步后手动过一遍，每项一两分钟：

- Copy Anchor：选中代码复制，粘贴结果正确；切换模式。
- JSON Explorer：粘贴一段 JSON；`cmd-;` 切换；Hover 一个嵌套字符串。
- Windsurf：出现修改预测并能接受；触发一次跳转；`windsurf: show last request` 能看到服务端返回的提示词。用 LS 后端时，退出后没有残留进程。
- 关掉三个功能的开关，确认按键和状态栏回到官方行为。

## 验收标准

| # | 标准 | 验证方法 |
|---|---|---|
| 1 | 用 `sync-upstream.sh` 完成一次真实的版本跟进（从一个稳定版 tag 到下一个） | 实际执行 |
| 2 | 同步过程中，冲突只出现在 `HOOKS.md` 列出的文件里 | 观察变基输出 |
| 3 | 脚本在冲突、检查失败、测试失败时都会停下，且能从备份标签恢复到同步前的状态 | 人为制造一次失败 |
| 4 | `bundle.sh` 产出的安装包能安装运行，与官方 `Zed.app` 并存 | 手动 |
| 5 | 安装包运行一周不出现更新提示 | 观察 |
| 6 | `HOOKS.md`、`CHANGELOG.md`、`回归清单.md` 存在并与实际一致 | 检查文件 |
| 7 | 从执行同步脚本到回归清单过完，人工操作时间不超过半小时 | 计时一次 |

## 约定

- 不向上游提交 fork 专有的改动。发现上游 bug 时，在干净的 `main` 上另开分支修复再提 PR。
- `fork` 分支上不合并 `main`，只变基，保持「上游 tag + 一串自己的提交」的线性历史。
- 新增挂钩之前先确认没有不改上游文件的办法；确实要加时，同一个提交里更新 `HOOKS.md`。

## 实际实现与用法

> 本节记录脚本的实际行为，以及和上面原文的出入。脚本在 `fork/` 下，`fork/CHANGELOG.md`、`fork/回归清单.md` 已建好。

### `fork/sync-upstream.sh <目标> [--skip-cargo] [--base <引用>] [--fork <分支>]`

- `<目标>`：上游稳定版 tag（如 `v1.30.1`）或 `upstream/main`。在主仓库根目录运行（`fork` 分支检出在那里），工作区必须干净（忽略未跟踪文件）。
- 步骤：`git fetch upstream --tags` → `git fetch . upstream/main:main`（不切分支，只允许快进）→ 打标签 `fork-backup/<年月日-时分秒>` → 算出当前基准 → `git rebase --onto <目标> <旧基准> fork` → `fork/check-hooks.sh <目标>` → `cargo check -p zed` → `cargo test -p fork_ext -p fork_copy_anchor -p fork_json_explorer -p fork_windsurf`。
- 当前基准的算法：在「`fork` 与 `upstream/main` 的分叉点」和「`fork` 可达的最近的 `v*` tag」里，取离 `fork` 更近（之间提交更少）的一个；算错时用 `--base <提交或 tag>` 手动指定。脚本会打印基准和将被重放的提交列表。
- 任何一步失败都停下，打印 `git status`、冲突文件和恢复命令：
  - 变基冲突：`git rebase --abort`（回到变基前），或手动解决后 `git add … && git rebase --continue`，再手动重跑检查。
  - 彻底回滚：`git rebase --abort 2>/dev/null; git checkout fork && git reset --hard fork-backup/<时间>`。
  - 不自动解决冲突，不推送。推送始终手动：`git push --force-with-lease origin fork`。
- `--skip-cargo`：跳过 cargo 两步，容器里只验证 git 部分时用。cargo 步骤要在宿主机运行；在 worktree 里跑时先设 `CARGO_BUILD_BUILD_DIR`（见 `0.整体设计.md` 第 9 节）。
- 目标是稳定版 tag、变基后 `crates/zed/RELEASE_CHANNEL` 不是 `dev` 时，脚本会**提示**加 H10，不自动改。
- 兼容 macOS 自带 bash 3.2（不用 GNU 专有选项、不用 `mapfile` 之类）。

### `fork/bundle.sh [--dry-run]`

- 包装 `script/bundle-mac <本机目标三元组>`，release 编译。`bundle-mac` 在没有 `MACOS_CERTIFICATE` 等变量时本来就走本地临时签名（`codesign --sign -`），所以不需要额外参数；脚本还会主动清掉环境里的证书、公证和 sentry 变量，保证走这条路径。
- 产物是 `target/<三元组>/release/Zed-<架构>.dmg`，复制到 `OUT_DIR`（脚本顶部配置，默认 `~/workspace/zed-fork-builds`，也可用环境变量 `FORK_BUILDS_DIR` 覆盖），文件名 `Zed-Dev-<上游版本>-fork.<fork 短提交>[-dirty]-<架构>.dmg`；上游版本取自 `crates/zed/Cargo.toml`。
- `--dry-run` 只打印版本、架构、环境变量、产物路径和前置检查结果，不编译。
- 前置检查：macOS、`cargo`/`rustc`/`xcrun`/`npm` 存在（`bundle-mac` 会 `npm install --global dmg-license`，首次还会 `cargo install cargo-bundle`），`RELEASE_CHANNEL` 必须是 `dev`（H10 之前基于 `main` 时本来就是 `dev`）。
- 版本字符串：构建时设 `ZED_COMMIT_SHA=<完整提交>-fork`（`crates/zed/build.rs` 会原样传给 `rustc-env`）。「关于」窗口显示的提交是这个值，完整版本为 `<上游版本>+dev.<完整提交>-fork`。限制：
  - 标记在构建元数据（`+` 之后）和提交号里，顶部的版本号（`CARGO_PKG_VERSION`）仍是上游的；要改只能改 `Cargo.toml`，那是上游文件，没做。
  - `ZED_APP_VERSION` 是运行时变量（`env::var`，不是编译期），用不上。
  - 提交号字段里带了 `-fork` 后缀，依赖它是纯十六进制的地方（例如生成提交链接）可能受影响；日常使用中没有已知问题，发现时再处理。
- 本机架构只有一种，不支持通用包和交叉编译。

### CI 打包 `.github/workflows/fork_bundle.yml`

- 手写的 workflow（不由 `cargo xtask workflows` 生成），复用官方 `script/bundle-linux`、`script/bundle-mac`、`script/bundle-windows.ps1`，产出六个包：Linux x86_64/aarch64 的 `tar.gz`、macOS aarch64/x86_64 的 DMG、Windows x86_64/aarch64 的安装器，外加各平台的 remote server。
- 官方的 runner（Namespace 付费机、自建 Windows 机）和签名、公证、Sentry 的 secrets fork 都没有，改用 GitHub 托管 runner，脚本在缺 secrets 时自动走未签名 / 本地临时签名路径。
- 触发：Actions 页面手动运行（`workflow_dispatch`，产物在该次运行的 Artifacts 里，保留 90 天；输入 `ref` 可构建没合入本文件的分支，例如 `gh workflow run fork_bundle.yml --ref fork -f ref=<分支>`）。手动运行默认勾选 `release`，构建完把全部产物发到 tag 为 `fork-<提交短哈希>` 的 prerelease，同一提交重复构建时覆盖产物；推送 `fork-v*` tag 时用该 tag 发 prerelease。
- `workflow_dispatch` 只认默认分支上的 workflow 文件。仓库默认分支是 `main` 时页面上看不到手动运行按钮，要么把 GitHub 上的默认分支改成 `fork`，要么只用 tag 触发。
- 版本标识与 `bundle.sh` 一致：`ZED_COMMIT_SHA=<提交>-fork`。
- 与官方的差异：Linux 在 Ubuntu 24.04 上编译（官方 20.04），要求 glibc ≥ 2.39；不打 Linux 的静态 `bwrap`；没有编译缓存，每次全量编译。
- `check-hooks.sh` 把 `.github/workflows/fork_*` 视为 fork 自有文件。

### 演练记录

脚本写完后在一次性克隆里演练过（上游用本地裸仓库模拟，克隆在宿主机 `/tmp` 下、容器里的 `.agents/tmp` 下各做过，演练完已删除），覆盖：
- 从 `main` 变基到新 tag 成功，并提示加 H10；再从该 tag 变基到下一个 tag。
- 变基冲突（上游改了 `main.rs` 里紧挨 H3 的一行）：停下，列出冲突文件和恢复命令，按提示命令恢复后 `fork` 回到同步前的提交。
- `check-hooks.sh` 失败（`fork` 上有未登记的 `README.md` 改动）、`cargo test` 失败（用假的 `cargo` 模拟）：都停下并给出恢复命令。
- 宿主机 bash 3.2 下重跑了成功和冲突两种情况。
