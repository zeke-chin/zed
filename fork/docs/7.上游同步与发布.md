# 7. 上游同步与发布

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。

## 目标

把「跟进上游新版本」和「打出自用安装包」做成固定流程，每次同步的人工工作量控制在半小时以内（不含编译时间）。

这一阶段的脚本可以在阶段 1 之后随时做，建议在第一次需要跟进上游之前完成。

## 要做的事

### 7.1 同步脚本 `fork/sync-upstream.sh`

输入一个上游稳定版 tag，执行：

1. `git fetch upstream --tags`。
2. 把 `main` 快进到 `upstream/main`。
3. 给当前 `fork` 分支打备份标签 `fork-backup/<日期>`。
4. 把 `fork` 变基到目标 tag。
5. 变基成功后依次执行 `fork/check-hooks.sh`、`cargo check -p zed`、各 `fork_` crate 的测试。
6. 任何一步失败就停下并打印当前状态，不自动解决冲突，不自动推送。

推送 `fork` 分支需要强制推送，这一步保持手动执行。

### 7.2 冲突处理手册 `fork/HOOKS.md`

对每个挂钩写明「上游改了这里时怎么重放」：

| 挂钩 | 冲突时的处理 |
|---|---|
| H1、H2 `Cargo.toml` | 接受上游版本，重新加上 fork 的几行 |
| H3 `main.rs` | 接受上游版本，在 `edit_prediction_registry::init` 之后重新加一行 |
| H4 注册表 | 接受上游版本，在 `assign_edit_prediction_provider` 函数体开头重新加挂钩；如果函数签名变了，同步调整 `fork_ext` 里的对应函数 |
| H5 `SettingsContent` | 接受上游版本，重新加字段和 `mod` 声明 |
| H6 `fork.rs` | 新文件，不会冲突；派生宏或属性变化时按编译错误修改 |
| H7 悬浮窗链接 | 接受上游版本，在 `open_markdown_url` 函数体开头重新加挂钩；函数被改名或拆分时，找到悬浮窗 `on_url_click` 最终调用的函数，把挂钩放过去 |

### 7.3 接口适配记录

上游改了 fork 用到的公开接口时，编译会失败。每次适配在 `fork/CHANGELOG.md` 里记一行：上游版本、哪个接口变了、怎么改的。重点关注这几个接口：

- `EditPredictionDelegate` 和 `EditPrediction`
- `SemanticsProvider`（方法增减会直接影响 Hover 装饰器）
- `Editor::register_action`、`Addon`
- `StatusItemView`
- `Settings` trait 和 `SettingsContent`

### 7.4 打包

- 用 `script/bundle-mac` 打出本机架构的 Zed Dev 安装包，使用本地临时签名。
- 包装成 `fork/bundle.sh`，产物放到固定目录，文件名带上游版本号和 fork 提交号。
- 应用的「关于」信息里能看出这是 fork 构建（例如版本字符串带 `fork` 后缀）。实现方式优先用构建时的环境变量，不改上游代码；做不到就保持原样。

### 7.5 回归清单 `fork/回归清单.md`

每次同步后手动过一遍，每项一两分钟：

- Copy Anchor：选中代码复制，粘贴结果正确；切换模式。
- JSON Explorer：粘贴一段 JSON；`cmd-;` 切换；Hover 一个嵌套字符串。
- Windsurf：出现修改预测并能接受；触发一次跳转；`windsurf: show last request` 能看到服务端返回的提示词。用 LS 后端时，退出后没有残留进程。
- 关掉三个功能的开关，确认按键和状态栏回到官方行为。

## 验收标准

| # | 标准 | 验证方法 |
|---|---|---|
| 1 | 用 `sync-upstream.sh` 完成一次真实的版本跟进（从一个稳定版 tag 到下一个） | 实际执行 |
| 2 | 同步过程中，冲突只出现在 `HOOKS.md` 列出的文件里 | 观察变基输出 |
| 3 | 脚本在冲突、检查失败、测试失败时都会停下，且能从备份标签恢复到同步前的状态 | 人为制造一次失败 |
| 4 | `bundle.sh` 产出的安装包能安装运行，与官方 `Zed.app` 并存 | 手动 |
| 5 | 安装包运行一周不出现更新提示 | 观察 |
| 6 | `HOOKS.md`、`CHANGELOG.md`、`回归清单.md` 存在并与实际一致 | 检查文件 |
| 7 | 从执行同步脚本到回归清单过完，人工操作时间不超过半小时 | 计时一次 |

## 约定

- 不向上游提交 fork 专有的改动。发现上游 bug 时，在干净的 `main` 上另开分支修复再提 PR。
- `fork` 分支上不合并 `main`，只变基，保持「上游 tag + 一串自己的提交」的线性历史。
- 新增挂钩之前先确认没有不改上游文件的办法；确实要加时，同一个提交里更新 `HOOKS.md`。
