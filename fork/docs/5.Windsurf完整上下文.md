# 5. Windsurf 完整上下文

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。

## 目标

把官方客户端发给云端的每一类上下文都补齐，让原生客户端的预测质量与官方 IDE 持平。完成后，同样的编辑场景下，fork 发出的请求与官方客户端发出的请求在内容上等价。

前置：阶段 4 完成。上下文的字段、大小上限、产生时机，以阶段 2 的「上下文对照表」（`fork/spike/结论.md`）为准。

## 基本方法

官方 LS 是闭源的，「LS 怎么选上下文」只能从它的输入输出推断。本阶段的工作方式是**逐类对齐**：

1. 取阶段 2 抓到的一个场景，看官方请求里这类上下文的内容。
2. 实现对应的采集器。
3. 在 Zed 里重现同一场景，用 `windsurf: show last request` 导出 fork 的请求。
4. 对比两份请求里这类上下文的差异，再对比服务端返回的提示词（`PreResponse.prompt`）。
5. 调到一致，把这个场景固化成测试。

服务端返回提示词这一点很关键：它直接显示了每类上下文最终在提示词里的样子，可以用来确认字段填对了没有。

## 要做的事

### 5.1 采集器框架

每类上下文一个采集器，实现同一个接口：

```rust
trait ContextCollector {
    fn name(&self) -> &'static str;
    fn collect(&self, request: &RequestContext, cx: &App) -> Task<Result<ContextPiece>>;
}
```

- 采集器之间互不依赖，并行执行，各有时间预算；超时的那一类本次不带，不拖慢整个请求。
- 每个采集器可以通过设置单独关闭（`fork.windsurf.context.<名称>`），用于排查和对比。
- 总大小有预算，超出时按优先级裁剪，优先级参考官方请求里各类上下文的占比。

### 5.2 完整的操作轨迹

`trajectory.rs` 记录用户在整个工作区里的操作序列，是最新 Tab 模型的主要输入。

| 步骤类型 | 触发 |
|---|---|
| 当前文档快照 | 每次请求 |
| 编辑 | 任意已打开 buffer 的编辑，相邻的连续输入合并成一步 |
| 查看文件 | 切换活动标签页、打开文件 |
| 查看代码片段 | 光标在某个符号定义内停留、跳转到定义 |
| 剪贴板 | 复制、剪切 |
| 诊断变化 | 当前文件新增或消除了诊断 |
| 预测反馈 | 接受、拒绝、忽略上一次预测 |
| 终端输出 | 仅当阶段 2 确认官方客户端会发 |

- 步骤的合并规则、保留数量和时间窗口按阶段 2 的结论。
- 轨迹按工作区维护，跨编辑器共享，随工作区关闭释放。
- 监听用上游公开的事件订阅（buffer 事件、工作区活动项变化），不加挂钩。

### 5.3 轨迹哈希与缓存

实现 `TabTrajectoryStepsV2` 的增量协议：已经发过的步骤只发哈希，新步骤发全文。

- 按服务端返回的 `cache_info_v2` 维护「服务端已知的步骤」集合。
- 收到 `MissingInformation` 时补发指定的步骤或文件。
- 缓存状态对不上时（服务端重启、会话过期）退回发全量，再重建。

### 5.4 相关代码检索

对应 `context_module_result`：与当前编辑位置相关、但不在当前文件里的代码片段。官方 LS 自己建索引来做，这里用 Zed 已有的能力实现：

| 来源 | 做法 |
|---|---|
| 光标附近标识符的定义 | 通过 `Project` 调 LSP 的跳转定义和类型定义，取目标符号的代码范围 |
| 当前文件的导入 | 解析导入语句，取被导入符号的定义或文件大纲 |
| 最近编辑和查看过的符号 | 来自轨迹 |
| 文件大纲 | Zed 的 tree-sitter 大纲 |

- 每个片段带路径、符号名、所属层级、行列范围，形状与官方请求一致。
- LSP 请求有时间预算，结果按 buffer 版本缓存。
- 选取和排序规则先按上面的优先级，再根据与官方请求的对比结果调整。

这一项是与官方差距最可能存在的地方：官方的选取规则看不到，只能逼近。

### 5.5 其余上下文

| 上下文 | 做法 |
|---|---|
| 其他打开的文件 | 阶段 4 已有，本阶段对齐排序规则、截断方式、每个文件带的元信息（是否有未保存修改、最近访问时间、可见范围） |
| 诊断 | 阶段 4 已有，本阶段对齐范围（只当前文件还是整个工作区）、严重级别过滤、数量上限 |
| 预测反馈 | `supercomplete_feedback_context`：最近若干次预测的内容和结果 |
| 补全菜单候选 | 仅当云端请求里有对应字段，且不改 `editor` crate 能拿到；否则不做 |

官方 agent 的对话历史（`cortex_trajectory`、`chat_messages`）不提供，Zed 里没有对应物。

### 5.6 反馈上报

按阶段 2 的结论实现接受和拒绝的上报：是单独的接口调用，还是只进入下一次请求的轨迹。只在官方客户端也会上报的情形下上报。

### 5.7 质量评估

建一套固定的评估场景 `fork/eval/windsurf/`，每个场景是「初始文件 + 一串编辑操作 + 期望的预测要点」：

- 改函数签名后更新调用处
- 改名后联动修改
- 新增字段后补全构造和使用处
- 用到未导入的符号后跳去补导入
- 有类型错误时按诊断修复
- 重复性编辑的第 N 次（模式延续）
- 跨文件：改了接口定义后更新另一个文件里的实现

至少 20 个场景，覆盖 3 种语言。每个场景在官方 IDE 和 fork 里各做一遍，记录是否出现了期望的预测。评估是人工执行的，结果记在 `fork/eval/windsurf/结果.md`。

### 5.8 性能

- 上下文采集全部在后台线程，不阻塞输入。
- 记录每次请求的分段耗时：采集、编码、首条增量、完成。
- 实测并记录：延迟（P50、P90）和 Zed 进程内存增量；如果阶段 8 的 LS 后端也实现了，做并排对比。

## 验收标准

| # | 标准 | 验证方法 |
|---|---|---|
| 1 | 阶段 2「上下文对照表」里官方客户端发的每一类上下文，fork 都有对应的采集器；没实现的有书面理由 | 对照表逐行核对 |
| 2 | 至少 5 个抓包场景做了请求对比：fork 的请求与官方请求相比，上下文类别没有缺失，服务端返回的提示词结构一致 | 对比记录存入 `fork/eval/windsurf/` |
| 3 | 评估场景里，fork 出现期望预测的比例不低于官方 IDE 的 90% | `结果.md` |
| 4 | 跨文件场景可用：改了一个文件后，预测跳到另一个文件并给出修改 | 评估场景 + 手动 |
| 5 | 接受一次预测后，下一次预测能延续同样的修改模式 | 评估场景 |
| 6 | 轨迹缓存生效：稳定编辑时请求体大小明显小于全量；人为清掉服务端缓存状态后能自动恢复 | 日志里的请求大小 + 假服务端测试 |
| 7 | 每个采集器有单元测试；轨迹的合并和裁剪规则有单元测试 | `cargo test -p fork_windsurf` |
| 8 | 关掉任意一个采集器后功能仍然正常，只是少一类上下文 | 逐个关闭后手动验证 |
| 9 | LSP 响应很慢或没有 LSP 的语言里，预测照常出现，延迟不受拖累 | 假 LSP 延迟测试 + 在纯文本文件里手动验证 |
| 10 | 在大仓库（例如本仓库）里连续编辑 30 分钟，输入没有可感知的卡顿，内存没有持续增长 | 手动，观察活动监视器 |
| 11 | 上下文采集的 P90 耗时在时间预算内，有日志记录 | 日志统计 |
| 12 | 一小时正常编码的请求数量与官方客户端同量级 | 对比日志计数与阶段 2 的记录 |
| 13 | 阶段 4 的全部验收标准仍然通过 | 回归 |
| 14 | 本阶段没有新增上游挂钩 | `fork/check-hooks.sh` |

## 待确认事项

- 能否在不改 `editor` crate 的前提下订阅到复制和剪切。订阅不到时，在请求时读一次系统剪贴板作为替代。
- 光标「停留」的判定阈值，以及查看代码片段步骤的粒度，按抓包里官方的行为定。
- LSP 跳转定义在请求量大时对语言服务器的压力，是否需要限频。
- 评估标准 3 里的 90% 是初定的门槛，第一轮评估后根据实际差距来源再调整。

## 不做的事

- 不自建向量索引或全仓库嵌入检索。先用 LSP 和 tree-sitter，评估结果显示检索是主要差距时再考虑。
- 不实现官方 IDE 专有的渲染方式，统一用 Zed 自带的预测渲染。
- 不做与预测无关的分析上报。
