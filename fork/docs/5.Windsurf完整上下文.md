# 5. Windsurf 完整上下文

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。
>
> **阶段 2 结论后的调整**（以 `fork/spike/结论.md` 第 4–6 节为准，与下文冲突时以这里为准）：
> - **去掉**「5.4 相关代码检索」和「其他打开的文件」：官方 LS 1.48.2 不在 `GetTab` 里发 `context_module_result` 和 `other_documents`。
> - **新增 Tab Jump**：跳转预测不在 `GetTab` 里。按结论问题 18 实现：每次触发并行发 `GetChatMessage`（`provider_source=PROVIDER_SOURCE_TAB_JUMP`、`internal_chat_model=MODEL_CHAT_20706`），提示词按抓到的模板在本地拼（`.scratch/tabjump_example.txt` 只在本机 spike worktree 里，不提交）。实现后 `supports_jump_to_edit` 由 `fork.windsurf.tab_jump` 决定。
> - **新增预测性预取和沿预测输入的本地缓存**：出预测后假设被接受、再请求一次；用户输入与预测前缀一致时本地裁剪当前预测。这是追平官方手感的关键（官方沿预测输入 1–5 ms，直连每次约 560 ms）。
> - 轨迹步骤实际只有 `CODE_ACTION`、`SUPERCOMPLETE_FEEDBACK`、`CLIPBOARD` 三类；`VIEW_FILE` / `VIEW_CODE_ITEM` 只出现在 Tab Jump 的文本提示词里；终端不做。
> - 哈希缓存：客户端不算哈希，服务端在 `PreResponse.cache_info_v2.hashes` 回传，下次原样带回；`MissingInformation` 时重发全量。
> - 反馈：进入轨迹（`SUPERCOMPLETE_FEEDBACK` 步骤 + `supercomplete_feedback_context`），另外发低频的 `ProvideFeedback`，让流量形态更接近官方客户端。
> - 轨迹保留上限阶段 2 没测出，自定（例如最近 50 步或 10 分钟）。

## 目标

把官方客户端发给云端的每一类上下文都补齐，让原生客户端的预测质量与官方 IDE 持平。完成后，同样的编辑场景下，fork 发出的请求与官方客户端发出的请求在内容上等价。

前置：阶段 4 完成。上下文的字段、大小上限、产生时机，以阶段 2 的「上下文对照表」（`fork/spike/结论.md`）为准。

## 基本方法

官方 LS 是闭源的，「LS 怎么选上下文」只能从它的输入输出推断。本阶段的工作方式是**逐类对齐**：

1. 取阶段 2 抓到的一个场景，看官方请求里这类上下文的内容。
2. 实现对应的采集器。
3. 在 Zed 里重现同一场景，用 `windsurf: show last request` 导出 fork 的请求。
4. 对比两份请求里这类上下文的差异，再对比服务端返回的提示词（`PreResponse.prompt`）。
5. 调到一致，把这个场景固化成测试。

服务端返回提示词这一点很关键：它直接显示了每类上下文最终在提示词里的样子，可以用来确认字段填对了没有。

## 要做的事

### 5.1 采集器框架

每类上下文一个采集器，实现同一个接口：

```rust
trait ContextCollector {
    fn name(&self) -> &'static str;
    fn collect(&self, request: &RequestContext, cx: &App) -> Task<Result<ContextPiece>>;
}
```

- 采集器之间互不依赖，并行执行，各有时间预算；超时的那一类本次不带，不拖慢整个请求。
- 每个采集器可以通过设置单独关闭（`fork.windsurf.context.<名称>`），用于排查和对比。
- 总大小有预算，超出时按优先级裁剪，优先级参考官方请求里各类上下文的占比。

### 5.2 完整的操作轨迹

`trajectory.rs` 记录用户在整个工作区里的操作序列，是最新 Tab 模型的主要输入。

| 步骤类型 | 触发 |
|---|---|
| 当前文档快照 | 每次请求 |
| 编辑 | 任意已打开 buffer 的编辑，相邻的连续输入合并成一步 |
| 查看文件 | 切换活动标签页、打开文件 |
| 查看代码片段 | 光标在某个符号定义内停留、跳转到定义 |
| 剪贴板 | 复制、剪切 |
| 诊断变化 | 当前文件新增或消除了诊断 |
| 预测反馈 | 接受、拒绝、忽略上一次预测 |
| 终端输出 | 仅当阶段 2 确认官方客户端会发 |

- 步骤的合并规则、保留数量和时间窗口按阶段 2 的结论。
- 轨迹按工作区维护，跨编辑器共享，随工作区关闭释放。
- 监听用上游公开的事件订阅（buffer 事件、工作区活动项变化），不加挂钩。

### 5.3 轨迹哈希与缓存

实现 `TabTrajectoryStepsV2` 的增量协议：已经发过的步骤只发哈希，新步骤发全文。

- 按服务端返回的 `cache_info_v2` 维护「服务端已知的步骤」集合。
- 收到 `MissingInformation` 时补发指定的步骤或文件。
- 缓存状态对不上时（服务端重启、会话过期）退回发全量，再重建。

### 5.4 相关代码检索

对应 `context_module_result`：与当前编辑位置相关、但不在当前文件里的代码片段。官方 LS 自己建索引来做，这里用 Zed 已有的能力实现：

| 来源 | 做法 |
|---|---|
| 光标附近标识符的定义 | 通过 `Project` 调 LSP 的跳转定义和类型定义，取目标符号的代码范围 |
| 当前文件的导入 | 解析导入语句，取被导入符号的定义或文件大纲 |
| 最近编辑和查看过的符号 | 来自轨迹 |
| 文件大纲 | Zed 的 tree-sitter 大纲 |

- 每个片段带路径、符号名、所属层级、行列范围，形状与官方请求一致。
- LSP 请求有时间预算，结果按 buffer 版本缓存。
- 选取和排序规则先按上面的优先级，再根据与官方请求的对比结果调整。

这一项是与官方差距最可能存在的地方：官方的选取规则看不到，只能逼近。

### 5.5 其余上下文

| 上下文 | 做法 |

| 诊断 | 阶段 4 已有，本阶段对齐范围（只当前文件还是整个工作区）、严重级别过滤、数量上限 |

官方 agent 的对话历史（`cortex_trajectory`、`chat_messages`）不提供，Zed 里没有对应物。

### 5.6 反馈上报

按阶段 2 的结论实现接受和拒绝的上报：是单独的接口调用，还是只进入下一次请求的轨迹。只在官方客户端也会上报的情形下上报。

### 5.7 质量评估

建一套固定的评估场景 `fork/eval/windsurf/`，每个场景是「初始文件 + 一串编辑操作 + 期望的预测要点」：

- 改函数签名后更新调用处
- 改名后联动修改
- 新增字段后补全构造和使用处
- 用到未导入的符号后跳去补导入
- 有类型错误时按诊断修复
- 重复性编辑的第 N 次（模式延续）
- 跨文件：改了接口定义后更新另一个文件里的实现

至少 20 个场景，覆盖 3 种语言。每个场景在官方 IDE 和 fork 里各做一遍，记录是否出现了期望的预测。评估是人工执行的，结果记在 `fork/eval/windsurf/结果.md`。

### 5.8 性能

- 上下文采集全部在后台线程，不阻塞输入。
- 记录每次请求的分段耗时：采集、编码、首条增量、完成。
- 实测并记录：延迟（P50、P90）和 Zed 进程内存增量；如果阶段 8 的 LS 后端也实现了，做并排对比。

### 5.9 Tab Jump（跳转预测，已实现）

代码：`crates/fork_windsurf/src/tab_jump.rs`（调度、定位、跳转交接）、`tab_jump/prompt.rs`（拼提示词）、`tab_jump/response.rs`（解析续写、文本定位）、`native/get_chat_message.rs`（发送与流式累积）。

**请求**：每次 `GetTab` 准备好后（有 key、不在退避、轨迹非空），若 `fork.windsurf.tab_jump` 为 true，同时向推理地址发 `GetChatMessage`（Connect 服务端流，超时 9992 ms），字段照抓包：`provider_source=TAB_JUMP`、`internal_chat_model=MODEL_CHAT_20706`（`ClientConfig.tab_jump_model`）、`request_type=COMMAND`、`configuration{num_completions 1, max_tokens 2048, temperature 0.1, top_k 50, top_p 1, 5 个 stop_patterns, fim_eot_prob_threshold 1, last_message_is_partial}`、`experiment_config` 带 `MODEL_CHAT_20706_TOKENS=10240`、`TAB_JUMP_CUMULATIVE_PROMPT_CONFIG`、`TAB_JUMP_MODEL_CONFIG`。设置为 false 时不发。Tab Jump 出错只记日志和调试视图，不影响状态栏和退避。

**提示词模板**（来源：spike 抓包 `captures/20261116-074332-capture` 里 27 条官方 `GetChatMessage`，系统提示 27 条完全一致；只复刻结构和固定文案，不含样例代码）：
1. `prompt` 字段：固定系统提示（`SYSTEM_PROMPT`）。
2. 文件查看：对近期编辑涉及的每个文件（其他文件在前，当前文件最后）发两条 USER 消息：「The USER performed the following action in the IDE:\nShow the contents of file X from lines a to b」+ 文件内容。内容取该文件在所展示的第一条编辑之前的全文（轨迹第一步的 `original_content`），没有就取当前全文；最后一条打 `EPHEMERAL` 缓存标记。
3. 近期编辑：按时间顺序，每步一条「The following changes were made by the USER to: X.\n[diff_block_start]\n…\n[diff_block_end]\n\nPlease note …」。hunk 从轨迹的 ±10 行 diff 重新渲染成 ±3 行上下文的 unified diff（间隔超过 6 行未改动就拆 hunk）。剪贴板步骤渲染为「I copied the following text to the clipboard: …」。最后一条打缓存标记。
4. `<additional_metadata>`：时间（本地时区，`Nov 16, 2026 at 7:44am, UTC-05:00` 格式）、Active Document + 语言枚举名、光标行（1 起）、Other open documents（已跟踪的其他 buffer，最多 10 个）、Active Code Item（光标所在最内层符号名，取不到就省略）、`@[路径:La-Lb] is a [Text Block]:` + 带 `<|cursor|>` 的当前文件，再接 `<user_request>`（与 `GetTab` 相同的 instruction）。
5. 最后一条 SYSTEM：半截 `<replace_file_content>{ "TargetFile", "CodeMarkdownLanguage", "Instruction", "Blocking": true, "ReplacementChunks": [{ "AllowMultiple": false, "TargetContent":`，并照官方带一个 `PROMPT_ANNOTATION_KIND_COPY` 注解（suffix 为当前文件 JSON 串，供服务端投机解码）。
- `num_tokens` 按「字节数 / 4」估算（抓包里的值约为每 3.8–4 字节一个 token）。

**截断预算**（按官方 `TAB_JUMP_CUMULATIVE_PROMPT_CONFIG` 的倍率，基数 10240 token，估算同上）：
| 部分 | 上限 | 依据 |
|---|---|---|
| 当前文件（metadata 里带光标的那份） | 4608 token（0.45×），超出时以光标行为中心上下交替扩展整行 | `persistent_active_document_multiplier` |
| 近期编辑 | 2560 token（0.5×0.5），且最多 30 条；从最新往旧取，超出即停 | `trajectory_context_multiplier` × `trajectory_truncation_multiplier` |
| 文件查看 | 合计 2560 token（0.25×），单个文件 ≤2048，以该文件第一处改动为中心开窗；当前文件优先，剩余不足 64 token 的不发 | `persistent_open_docs_multiplier`、`persistent_max_tokens_per_open_doc` |

**解析与定位**：续写从 `"TargetContent":` 之后开始，按 JSON 读出 `TargetContent` 和 `ReplacementContent`（流被截断、格式不符都放弃；`TargetContent` 为空表示没有跳转）。去掉 `<|cursor|>` 后在目标文件当前文本里做精确匹配：先找当前文件；当前文件里没有时，再在提示词里展示过的其他文件里找，恰好一个文件里唯一出现才算跨文件跳转。匹配不唯一或找不到就放弃。`<|cursor|>` 缺失时以第一处修改的位置作为跳转点。CRLF 统一成 `\n`（Zed buffer 内部就是 `\n`）。

**跳转之后**：选「把 `ReplacementContent` 直接作为该处的修改预测」，不在 `TAB_JUMP_ACCEPT` 时再请求 `GetTab`。理由：结论问题 18 说明 `ReplacementContent` 就是跳过去后的修改；少一次往返，结果确定、可测试。接受后的下一次触发照常请求 `GetTab`。
- 优先级：`GetTab` 给出了修改就用 `GetTab` 的（Tab Jump 照常跑完，只记录到调试视图）；`GetTab` 没有修改时才等 Tab Jump 的结果。
- 同文件：给出目标处的 `EditPrediction::Local`。修改离光标远时，编辑器因 `supports_jump_to_edit()=true` 显示「跳转到修改」，Tab 跳过去后同一份修改作为普通预测显示，再按 Tab 接受。
- 跨文件：在原编辑器给出 `EditPrediction::Jump{目标 buffer 快照, <|cursor|> 处的锚点}`，同时把修改作为「落点」存在全局状态里；编辑器打开目标文件后，那里的 delegate 在 `refresh`/`suggest` 时取走落点显示修改。目标 buffer 没加载时，在请求发出的同时（refresh 阶段）通过 `Project::open_buffer` 预先打开。原文件之后又被编辑、或落点已被取走/丢弃时，原编辑器不再给出跳转。
- `supports_jump_to_edit` 是无参的静态函数，读不到设置，所以用一个进程级开关跟随 `fork.windsurf.tab_jump`（设置变化时同步）。

**调试**：`windsurf: show last request` 的输出多了 `tab_jump` 字段：最近一次 Tab Jump 的请求（api_key/user_jwt 只留长度，长消息截断到 2000 字节，COPY 注解只留长度）、续写原文、stop_reason、耗时、结果（`jump within the file` / `jump to another file` / 放弃原因）和定位到的目标。

**真实验证**：`tests/live_tab_jump.rs`（`#[ignore]`，需要 `WINDSURF_API_KEY`）。三个场景各发一次（改方法名、加参数、改属性名），串行间隔 2.5 秒；2026-11-16 实测三次都被接受，首个增量 245–1138 ms、完成 671–2175 ms，三次跳转都落在合理位置（其中两次正是编辑所暗示的调用点）。

## 实现记录（W5-core）

本节记录实现中查清的事项和与正文的出入。依据：`fork/spike/结论.md`，以及对阶段 2 抓包（`captures/20261116-074332-capture`，只在本机 spike worktree）的再次解码。

### 5.1 采集器框架：不做

现有结构已经够用，没有为框架而框架。理由：
- 官方 `GetTab` 实际只有四类上下文：当前文档 + 窗口（`command_intent_info`）、轨迹、诊断、反馈上下文。去掉检索和其他打开的文件以后，没有耗时的采集器（LSP 跳转之类），全部是对 buffer 快照的同步计算（拷贝文本、算行级 diff），耗时记在日志的 `context N ms` 里；还没有在真实使用中统计。
- 「互不依赖、并行、各自超时」针对的是慢的 LSP 采集器，现在不存在。
- 新增的轨迹步骤类型直接进 `trajectory.rs`；剪贴板、反馈、预取各自一个模块（`clipboard.rs`、`feedback.rs`、`prefetch.rs`），哈希缓存是 `trajectory_cache.rs`。
- 不加 `fork.windsurf.context.<名称>` 开关：加字段要改 `settings_content` 里的 fork 设置结构，收益只是排查。验收 8（关掉任意一类仍能工作）由测试覆盖：没有诊断、没有反馈、没有剪贴板的请求都是正常路径。

### 5.2 轨迹

| 步骤 | 产生时机 | 内容 |
|---|---|---|
| `CODE_ACTION` | 编辑在触发（发请求）或 IDE 动作（复制、接受、拒绝）时切分成一步 | 同阶段 4；每个文件第一步带 `original_content` |
| `SUPERCOMPLETE_FEEDBACK` | 接受、有意拒绝 | `completion_id`、`feedback_type`（`accept` / `reject`）、`feedback_reason`（拒绝时 `intentional`）、`document`（反馈时的全文，不带 `cursor_offset` 和 `language`，与抓包一致）、`feedback_delay_ms`（从首次显示 `did_show` 到反馈）、`provider_source=SUPERCOMPLETE` |
| `CLIPBOARD` | 复制后 5 秒内的第一次请求 | `content`；≤1000 字符；`metadata.completed_at` 与 `created_at` 相同（抓包如此） |

- **接受时的切分**：接受前用户打的字、接受的预测各成一步，顺序是「打字 → 反馈 → 接受的修改」，与抓包里官方完整重发时的顺序一致。编辑器先把预测写进 buffer 再调 `accept`，所以 delegate 记下最近一次 `suggest` 时的快照（`Trajectory::commit_buffer_at`），用它切开两段。
- **合并规则与问题 9 的出入**：抓包里官方 LS 的最后一个 `CODE_ACTION` 会跨触发继续增长（例如 572 号请求和 700 号请求里同一步变长），之后又被拆开。规则看不出来，所以按问题 9 的文字（「触发或 IDE 动作时切分」）实现。好处是已提交的步骤不再变化，哈希前缀保持最长。
- **保留上限**：最多 50 步、10 分钟（`trajectory.rs::MAX_STEPS`、`MAX_AGE`），替换阶段 4 的 64 步。从头部删步骤会让所有缓存哈希失效（下一次只能发全量），所以按批删：超过 50 步时删到 40 步；最老的一步超过 10 分钟时，删掉所有超过 8 分钟的。正常编辑时最多每 2 分钟发一次全量。
- **剪贴板来源**：用 `cx.observe_keystrokes`。它在按键对应的动作处理完之后才调用，这时剪贴板已经写好。任何命名空间下名为 `Copy`、`Cut`、`CopyAndTrim` 的动作都会记录当时的剪贴板（编辑器、终端都覆盖）。不经按键的复制（菜单点击、其他应用里复制）在 `Paste` 动作时补记：剪贴板内容与上次记录的不同，就算作这时复制的。不在每次请求时读系统剪贴板，原因有二：一是拿不到复制时间，「5 秒内」无法判断；二是会把很久以前复制的内容当成新的。不改 `editor` crate，不加挂钩。
- **像密码的内容**：以常见密钥前缀开头（`sk-`、`ghp_`、`AKIA`、`eyJ`、`-----BEGIN`、`devin-session-token` 等）；或者是不含空白、8–128 字符、混用了至少三类字符（小写、大写、数字、符号）的单个词。代码片段一般带空白，不受影响。
- 复制会切分编辑步骤，剪贴板步骤插在复制之前的步骤之后（抓包里是 `CLIPBOARD` 在粘贴产生的 `CODE_ACTION` 之前）。

### 5.3 哈希缓存

- 每个服务端回传的哈希与「发出的那一步」的指纹（protobuf 编码的哈希）一一对应。下次请求取**指纹仍相同的最长前缀**放进 `trajectory_steps_v2.hashes`，其余步骤放进 `steps_after_hashes`，`cortex_trajectory.steps` 留空。这与抓包吻合：官方 LS 带回的哈希经常少于上次回传的数量。原因是预测性请求的最后一步是假设的接受，以及步骤在变化。
- `MissingInformation`：清缓存，用同一个请求带全量轨迹重发一次（同一个 `trigger_id`）。再缺就放弃本次请求，记 warn 日志，状态栏显示协议错误，缓存保持清空，下次从全量开始。没有回 `cache_info_v2` 时也清空缓存。
- 日志每次请求记 `request N bytes, k cached + m new steps`；重发时记 `all n steps after the server lost k cached`。
- 实测（2026-11-16，`live_trajectory_cache_and_prediction`，小文件 10 行）：全量 3941 字节 → 带 1 个哈希、多一步的请求 3771 字节（服务端接受，没有 `MissingInformation`，回 2 个哈希）→ 预测性请求带 2 个哈希 3870 字节（回 3 个哈希）。请求体主要是当前文档全文，所以文件越大、轨迹越长，差距越明显；假服务端测试里 200 行的文件第三次请求小于第一次的 2/3。

### 预测性预取与沿预测输入的本地缓存

- **沿预测输入**：复用阶段 4 已有的 `edit_prediction_types::interpolate_edits`（codestral、zeta 也这么做）。用户输入与预测前缀一致时，`refresh` 直接返回、不发请求，`suggest` 显示裁剪后的预测。本阶段加了计数（`local_cache_hits`）。
- **预取**（`prefetch.rs`）：出预测后立即按「接受后的文档」发一次 `GetTab`：
  - 文档是 buffer 应用预测后的全文；光标放在最后一处修改的末尾；`input_document.cursor_position{row, col(字符)}` 只在预测性请求里填（抓包里官方就是这样区分的）。
  - 轨迹是当前步骤再加「baseline → 接受后文本」一步；不带诊断。
  - `metadata.trigger_id` 沿用触发它的请求（官方同一个触发的多个 `GetTab` 共用 `trigger_id`）。
- **命中**：buffer 全文与预取假设的文本完全相同时（先比长度），直接用预取结果，不发请求。接受（Tab）和照着预测打完都会走到这里。预取还在途时，触发会等它返回，不另发请求；如果预取失败，再补发一次普通请求。命中后显示的预测会再触发一次预取，形成链。
- **请求量**：每个显示的预测最多一次预取；命中预取本身就是对一个触发的应答。所以每个触发最多 2 个 `GetTab`（官方 1–3 个）。用户做了别的操作（输入不符、拒绝）时，丢掉预取并取消在途的 HTTP 请求。退避中或有错误时不发预取。抓包里官方接受后（`after_accept` 触发）也没有发新的 `GetTab`，与这里的行为一致。

### 与 Tab Jump 共存

- 普通触发：`GetTab` 和 Tab Jump 的 `GetChatMessage` 并行（Tab Jump 的逻辑不变）。`GetTab` 有修改预测时用它，并为它发一次预测性请求。
- 预取命中、预取结果没有修改时，补发这个触发的 Tab Jump，跳转结果照常显示；预取结果有修改时不发 Tab Jump，与普通触发的优先级一致。
- 预测性请求本身不并行发 `GetChatMessage`（官方会发，每个触发 1–3 个）。这样请求量更少，代价是预取命中时跳转要多等一次 `GetChatMessage`。
- 本地裁剪、预取、反馈只作用于 `GetTab` 的修改预测。Tab Jump 的预测（包括跨文件落点）不发预测性请求，也不记反馈。官方拒绝跳转时会在反馈上下文里写 `tabjump_suggestion`，这一点还没做。
- Tab Jump 的提示词从轨迹取历史，会用到新增的 `CLIPBOARD` 步骤。

### 5.5 诊断

按问题 7：光标行 ±10 行、最多 5 条、不按严重级别过滤（`all_diagnostics`），排序为错误优先，其次离光标近的。字段对齐抓包：`range` 只有 `start_position` / `end_position`（UTF-16 列），不再填 `start_offset` / `end_offset` 和 `language`。另外 `input_document.language` 官方也不填，已去掉（顶层 `language` 照填）。

### 5.6 反馈

- `supercomplete_feedback_context.feedback`：抓包里**接受和有意拒绝都会进入**，而且整个会话一直保留（问题 7 写的「最近一次被接受的」不准确）。实现保留最近 5 条，接受和拒绝都放。条目字段：`accepted` / `intentional_reject`、`completion_id`、`timestamp_ms`、`diff_suggestion{path(file URI), selection_start_line, selection_end_line, character_diff, cursor_position, old_str, unified_diff}`。
  - `character_diff` 是窗口 old → new 的字符级变化（连续同类合并）；`unified_diff` 是整个窗口的行级 diff，同一块里先插入后删除（与抓包一致）。
  - 抓包里 `diff_suggestion` 的行范围比请求窗口大（0–25），原因不明；这里用请求窗口。
- `completion_id` 每个预测一个 uuid。`ProvideFeedback.prompt_id` 是产生该预测的 `GetTab` 的 `prompt_id`，与抓包一致。
- `ProvideFeedback`：`source` 用 `COMPLETION_SOURCE_NETWORK`，预取命中的预测用 `COMPLETION_SOURCE_CACHE`（后者是推测，抓包里没有这个场景）。`feedback` 为 ACCEPT / REJECT，拒绝时 `extra_info=INTENTIONAL_REJECT`，另外填 `timestamp_unix_ms`、`feedback_delay_ms`、`provider_source`；metadata 带 jwt。限频：全局 5 秒内最多一次，超出的只进轨迹不上报；失败只记 warn 日志。实测一次，返回成功。
- 「有意拒绝」：Zed 在 Esc 和选择补全菜单项时都报 `Rejected`，两者都按有意拒绝处理；`Ignored`（光标移走、失焦等）不算反馈。沿预测打完不记反馈（官方有 `TYPED_AS_SUGGESTED`，抓包里没出现）。

### 5.8 性能日志

每次 `GetTab` 一行 info：类型（trigger / predictive）、总耗时、上下文采集耗时、首条增量、请求字节数、缓存 / 新步骤数、结果。累计计数（`requests`、`predictive_requests`、`local_cache_hits`、`predictive_hits`、`full_resends`、`feedback_reports`）在 debug 日志里，也显示在 `windsurf: show last request` 的 `stats` 字段中。P50 / P90 和内存还没有统计（需要手动使用一段时间后从日志算）。

### 需要手动验收

- 在 macOS 上按 Cmd-C 复制后 5 秒内输入，`show last request` 的轨迹里出现 `CLIPBOARD`；菜单复制、其他应用复制后粘贴也能出现。
- 接受预测后下一条预测几乎立即出现（预取命中），日志里 `predictive_hits` 增长、没有对应的 trigger 请求。
- 长时间编辑后观察日志里的请求字节数和全量重发频率（预期最多每 2 分钟一次）。

## 不做的事

- 不自建向量索引或全仓库嵌入检索。先用 LSP 和 tree-sitter，评估结果显示检索是主要差距时再考虑。
- 不实现官方 IDE 专有的渲染方式，统一用 Zed 自带的预测渲染。
- 不做与预测无关的分析上报。
