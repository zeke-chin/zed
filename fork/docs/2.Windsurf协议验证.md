# 2. Windsurf 协议验证

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。

## 目标

弄清楚 Windsurf（现 Devin）官方客户端与云端之间的 Tab 协议，在 Zed 之外用独立脚本**直连云端**调通 `GetTab`，判断「用 Rust 重写、不依赖官方 LS」是否可行。

这一阶段不写任何 Zed 代码，可以和阶段 1 并行。结论决定后面走原生方案（阶段 4、5）还是备选方案（阶段 8）。

## 背景

官方 IDE 的链路有两段：

```
IDE 扩展 ──①──▶ 本地 Language Server（LS，闭源 Go 程序）──②──▶ 云端 ApiServerService
```

- 第 ① 段是 IDE 把原始上下文交给 LS，接口是 `LanguageServerService/HandleStreamingTabV2`。
- 第 ② 段是 LS 加工后调云端，接口是 `ApiServerService/GetTab`。

原生方案要自己实现 LS 的工作，所以**第 ② 段是重点**。第 ① 段用来对照：同一次按键，IDE 给了 LS 什么，LS 又给了云端什么，差出来的部分就是 LS 做的加工。

## 凭据与本机配置：一个存放位置，两种写入方式

和正式实现的结构一致（见 `0.整体设计.md` 第 8.1 节）：正式实现存在 Zed 的 `settings.json` 里，验证阶段还没有 Zed 代码，存放位置是 `fork/spike/.env`，所有脚本只从这个文件读。这个文件被 git 忽略，仓库里只提交模板 `fork/spike/.env.example`：

```sh
# 必填：Windsurf / Devin 的 api_key
WINDSURF_API_KEY=
# 选填：LS 二进制路径，留空时脚本按常见安装位置查找并打印找到的路径
WINDSURF_LS_PATH=
# 选填：API 地址，留空用默认值
WINDSURF_API_SERVER_URL=
```

写入 `WINDSURF_API_KEY` 有两种方式：

| 方式 | 做法 |
|---|---|
| 从本机导入 | 执行导入命令（例如 `fork/spike/run import-key`），脚本去本机 Devin/Windsurf 的登录数据里找，找到后写入 `.env` |
| 手动填写 | 直接编辑 `.env` |

- 导入只在执行导入命令时发生，其他脚本不读本机登录数据。
- 导入命令打印找到的来源路径和打码后的密钥；`.env` 里已有值时先确认再覆盖。
- `WINDSURF_API_KEY` 为空时，其他脚本直接退出，并提示上面两种写入方式。
- 脚本输出和保存的示例里，凭据一律打码。

## 要做的事

### 2.1 提取最新的 proto

1. 找到本机官方 LS 二进制，记录版本。
2. 从二进制里提取内嵌的 proto 描述符，还原出 `.proto` 文件。Go 程序会把描述符编进二进制，逆向仓库的 proto 就是这么来的。
3. 和 `modelgate`、`oh-my-pi` 的版本做差异对比，记录 Tab 相关消息的变化。
4. 把提取过程写成脚本 `fork/spike/extract-proto`，以后官方升级时可以重跑。

### 2.2 抓取官方客户端的真实流量

两段都要抓，并且能按时间对应起来：

- 第 ① 段（IDE → LS）：本机回环上的明文 HTTP，加一层转发代理记录。
- 第 ② 段（LS → 云端）：LS 启动参数里可以指定 API 地址，把它指向本机的记录代理，由代理转发到真实云端。这样不需要解 TLS。指定不了的话再考虑中间人代理。

抓取场景至少包括：打开文件后第一次触发、连续输入、改名后的联动修改、跳转、接受、拒绝、切换文件、有诊断错误时、复制粘贴后。

原始记录存到 `fork/spike/captures/`，这个目录被 git 忽略（里面有凭据和代码内容）。

### 2.3 直连云端调通

用脚本（Python 或 TypeScript）不经过 LS，直接向云端发 `GetTab`：

1. 先原样重放一条抓到的请求，确认能拿到同样的响应。
2. 再逐个字段替换成自己构造的值，找出哪些字段必填、哪些被校验。
3. 最后用完全自己构造的请求（自己的文档、自己的轨迹）拿到合理的预测。

### 2.4 备选方案的最小验证

顺手确认备选路线可用：用脚本拉起官方 LS，调通一次 `HandleStreamingTabV2`。只验证能通，不深入。

## 要回答的问题

### A. 认证与连接

1. `api_key` 是什么格式，本机登录数据存在哪个文件的哪个字段（导入用），用户手动从哪里能拿到（填写用）。
2. 云端请求直接带 `api_key`，还是要先换成短期令牌。要换的话，换取和刷新接口是什么，有效期多长。
3. `metadata` 里每个字段的含义，哪些必填，哪些被服务端校验（客户端名称、版本、设备标识、会话标识等）。
4. 请求头有哪些，有没有签名、时间戳之类的防重放字段。
5. 云端地址是什么，是否按区域或账号类型不同。
6. 要不要发心跳或 `Ping`，不发会怎样。

### B. 请求内容

7. `unified_prompt_components` 里官方客户端实际填了哪些字段，各自的内容和大小上限是多少。
8. 当前文档和光标是通过哪个字段或哪种轨迹步骤传的。
9. `trajectory_steps_v2` 里实际出现哪些步骤类型，各在什么用户操作下产生，保留多少步、多长时间。
10. 步骤的哈希怎么算。重放时用抓到的哈希可以过，自己算的哈希能不能过，是这一条的关键。
11. `MissingInformation` 在什么情况下返回，客户端应该怎么补发。
12. `cache_info_v2` 和 `uris_to_hashes` 怎么用，不实现缓存（每次发全量）是否可行。
13. `context_module_result` 里的检索结果是什么形状，LS 用了什么规则选片段（从多组「输入对照输出」推断）。
14. `experiment_config`、`model`、`provider_source` 填什么，是固定值还是从某个接口取。
15. 位置单位：行号从 0 还是 1 开始，列按字节、UTF-16 还是字符计。

### C. 响应内容

16. 一次请求返回几条 `DeltaTab`，`is_complete` 之前的增量怎么拼接。
17. `DeltaSupercomplete` 的 `start_line`、`end_line`、`delta_old_str`、`delta_new_str` 的确切语义。
18. `DeltaTabJump` 之后是否要立刻再发一次请求。
19. 跨文件的预测和跳转是怎么表示的（`path` 字段）。
20. 典型延迟：首条增量和完成，P50 和 P90，各测 20 次以上。直连云端和经过 LS 各测一组。

### D. 反馈与副作用

21. 接受和拒绝各自要调哪个接口，或者只是进入下一次请求的轨迹。
22. 官方客户端还会定期上报哪些分析类请求，不发有没有可见影响。

## 决策点

| 结果 | 后续 |
|---|---|
| 自己构造的 `GetTab` 请求能拿到合理预测，哈希和认证都弄清了 | 走原生方案：阶段 4、5 |
| 能调通但部分机制没弄清（例如哈希只能重放） | 写明缺口和绕过办法；能绕过就走原生方案，绕不过走备选 |
| 直连云端调不通，LS 桥接可用 | 走备选方案：阶段 8 |
| 两条路都不通 | Windsurf 线搁置，直接做阶段 6 |

## 注意事项

- 测试请求的频率不超过正常打字触发的频率，不做压力测试，不并发重放。
- 逆向调用可能违反 Windsurf 的服务条款，直连云端比调用官方 LS 更容易被识别，存在封号风险。只用自己的账号测试。
- 抓包数据里有代码内容和凭据，只留在本机。
