# 1. Fork 脚手架

> 本仓库是 zed-industries/zed 的个人 fork。整体设计见 `0.整体设计.md`。

## 目标

把仓库整理成 fork 的形态，建好自有 crate 和全部上游挂钩，编译出一个行为与官方完全一致的 Zed Dev。这一阶段不实现任何功能。

## 前置条件

- GitHub 上的 `zeke-chin/zed` 已存在，是官方仓库的 fork。
- git 操作在宿主机执行：`ssh -p 10023 zeke@172.30.0.2`。
- `gh` 的情况：容器内已登录可用；宿主机装在 `/opt/homebrew/bin/gh`，但通过 ssh 调用时报令牌无效。GitHub 接口操作用容器内的 `gh`；宿主机上 `git push` 能否通过认证要在本阶段第一步验证。

## 要做的事

### 1.1 远程与分支

1. 把现有 `origin` 改名为 `upstream`，新增 `origin` 指向 `zeke-chin/zed`。
2. `upstream` 的推送地址设为无效值，防止误推。
3. 取最新的上游稳定版 tag，从它创建 `fork` 分支。
4. `fork/docs/` 作为 `fork` 分支的第一个提交。

### 1.2 自有 crate

创建四个 crate，按仓库规范在 `Cargo.toml` 里用 `[lib] path = "src/<crate 名>.rs"` 指定入口：

| crate | 本阶段内容 |
|---|---|
| `fork_ext` | `init`、`ForkSettings`、编辑器与工作区挂载框架、`assign_edit_prediction_provider`（暂时恒返回 `false`） |
| `fork_copy_anchor` | 空的 `init` / `attach_editor` / `status_items` |
| `fork_json_explorer` | 同上 |
| `fork_windsurf` | 空的 `init` |

### 1.3 上游挂钩

按 `0.整体设计.md` 第 5 节落地 H1–H6，每处加 `// FORK:` 注释。

`crates/settings_content/src/fork.rs` 里定义完整的 `ForkSettingsContent`（含三个功能的全部字段），后续阶段不再改这个文件的结构。

### 1.4 键位加载

`fork/keymaps/default-macos.json` 先放一个空数组，`fork_ext::init` 里用 `KeymapFile::load` 加载。需要确认加载时机在官方默认键位之后、用户键位之前，使用户键位能覆盖 fork 的默认键位。

### 1.5 文档与检查

- 创建 `fork/HOOKS.md`，列出 H1–H6 的文件、行为、原因。
- 创建 `fork/check-hooks.sh`：对比 `rg "FORK:"` 的结果与 `HOOKS.md`，并统计 `fork` 分支相对基准 tag 改动的上游文件，超出清单就报错。

### 1.6 首次编译

在宿主机执行 `cargo run`，确认 Zed Dev 能启动。首次全量编译预计 20–40 分钟。

## 验收标准

| # | 标准 | 验证方法 |
|---|---|---|
| 1 | `git remote -v` 显示 `origin` 为 `zeke-chin/zed`，`upstream` 为官方且不可推送 | 宿主机执行命令 |
| 2 | `fork` 分支基于某个上游稳定版 tag | `git describe --tags --abbrev=0` |
| 3 | `cargo check -p zed` 与 `./script/clippy` 通过 | 宿主机执行 |
| 4 | Zed Dev 能启动，与官方 `Zed.app` 并存，数据目录互不影响 | 两个应用同时打开 |
| 5 | 相对基准，改动的上游已有文件只有 `HOOKS.md` 清单里的 7 个（H1–H5、H8、H9） | `fork/check-hooks.sh` |
| 6 | `settings.json` 写入 `"fork": { "copy_anchor": { "enabled": false } }` 不报错，写错字段类型时有设置错误提示 | 手动 |
| 7 | 设置里 `"fork"` 键有自动补全（说明 JSON Schema 已生成） | 手动 |
| 8 | 日志里能看到 `fork_ext` 对每个新编辑器的挂载记录 | 打开文件后查看 `zed: open log` |
| 9 | Zed Dev 不提示更新 | 观察 |

## 待确认事项（已查清）

- **键位来源和优先级**：`KeymapFile::load` 本身不设来源，由调用方 `set_meta`，fork 标为 `KeybindSource::Default`。更重要的是 `reload_keymaps` 每次都先 `clear_key_bindings()`，在 init 里绑定一次会在用户改 keymap 后丢失。因此新增挂钩 H8：在 `load_default_keymap` 末尾调用 `fork_ext::load_default_keymap`，顺序是官方默认 → fork → 用户。
- **settings_ui 覆盖检查**：没有针对 `SettingsContent` 字段的覆盖性测试，不需要豁免。
- **H4 参数**：`editor`、`trigger`、`window`、`cx` 足够，`editor.project()` 和 `editor.buffer()` 能拿到 delegate 需要的上下文。
- **H5 比预想多一处**：`SettingsContent` 的反序列化由 `flattened_deserialize!` 宏按字段列表生成，`fork` 也要加进宏的 `options` 列表。
- **基准**：先基于上游 `main` 开发，跟进上游时再改为稳定版 tag，届时加 H10（`RELEASE_CHANNEL` 改为 `dev`）。
- **H9**：`crates/settings/src/vscode_import.rs` 用结构体字面量列出了 `SettingsContent` 的全部字段，加字段后要补 `fork: None`，否则编译不过。

## 不做的事

- 不实现任何功能逻辑。
- 不改应用名称和图标，沿用 Zed Dev。
