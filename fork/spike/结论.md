# 阶段 2 结论：Windsurf（Devin）Tab 协议验证

> 对应 `fork/docs/2.Windsurf协议验证.md`。本文是阶段 4、5、8 协议细节的依据，和设计文档冲突时以本文为准。
> 文中密钥、令牌一律打码；路径里的用户名、工作区路径只是测试目录。

## 0. 一句话结论

**自己构造的 `GetTab` 请求可以直连云端拿到合理预测，认证和轨迹哈希都弄清了，决定走原生方案（阶段 4、5）。**
主要的额外工作是 Tab Jump：它不在 `GetTab` 里，而是 LS 在本地拼好提示词，调 `GetChatMessage` 得到的。提示词格式已经抓到，直连重放也能通，但要自己实现（见问题 18、第 6 节）。

## 2. 怎么做的、怎么复现

所有命令都经 `fork/spike/run`，第一次运行时会在 `fork/spike/.venv-<系统>` 自动建 venv，不做全局安装。

| 命令 | 作用 | 在哪跑 |
|---|---|---|
| `run import-key [-y]` | 从本机 Devin 登录数据导入 `api_key` 到 `.env`（**唯一**读本机登录数据的地方） | Mac |
| `run get-tab` | **验收标准 3**：不经 LS，用自己构造的文档和编辑轨迹直连云端发 `GetTab`，打印预测的 diff。`--demo complete`、`--file F --line L --col C` 可换输入 | Mac / 容器 |
| `run ls-tab` | **验收标准 7**：拉起官方 LS，调一次 `HandleStreamingTabV2` | Mac / 容器 |
| `run capture [场景...]` | 拉起 LS，按场景模拟 IDE 扩展的调用顺序，**两段流量**写入 `captures/` | 容器（见下） |
| `run analyze [会话]` | 按 `trigger_id` 把 IDE→LS 和 LS→云端对应起来，统计每次触发的上下文 | 任意 |
| `run decode [会话] [--full]` | 把记录解码成 JSON（凭据打码） | 任意 |
| `run probe <实验...>` | 字段替换实验（串行，间隔 ≥2 秒） | 任意 |
| `run latency direct\|ls\|ls-diverge` | 延迟测量 | 任意 |

**两段抓包的做法**

- 第 ① 段（IDE→LS）：没有用 Devin.app 本身，而是由脚本按 `extension.js`（官方扩展源码）的调用顺序驱动 LS：Connect（`application/proto`，头 `x-codeium-csrf-token`）+ LSP（`didOpen`/`didChange`）+ `RefreshContextForIdeAction`（STARTUP / ACTIVE_EDITOR_CHANGED / 500ms 防抖的 SELECTION_CHANGED）+ `HandleStreamingTabV2` + `ProvideCompletionFeedback`。这样不需要有人在 Devin 里打字。
- 第 ② 段（LS→云端）：`--api_server_url` 只管一部分请求，**`GetTab` 走的是 unleash 开关下发的推理地址**，不经过这个参数，所以改走 TLS 终止：在 Linux 容器里跑同一构建的 Linux 版 LS，`SSL_CERT_FILE` 指向「系统 CA + 自签 CA」，`/etc/hosts` 把 codeium 的几个域名指到本机，`lib/mitm.py` 在 127.0.0.1:443 终止 TLS 后转发到真实 IP（只改容器，不动宿主机，退出时还原 hosts）。macOS 上 Go 走系统钥匙串验证证书，不改钥匙串就没法做，所以没在 Mac 上抓第 ② 段。
- 对应关系：IDE 给 LS 的 `metadata.trigger_id`，LS 原样带到 `GetTab` 和 `GetChatMessage` 的 `metadata.trigger_id`。`run analyze` 就按这个字段做对应。

**场景覆盖**（最近一次完整记录：`captures/*-capture`）

| 场景 | 结果 |
|---|---|
| 打开文件后第一次触发（不编辑，只移动光标） | LS 发出**空轨迹**的 `GetTab`，云端回 internal error，LS 对 IDE 一直不响应（我们 15 秒超时）。见问题 9 |
| 连续输入 | ✓ 修改预测；后续按键命中 LS 本地预测缓存 |
| 接受 | ✓ 上报 + 轨迹多出反馈步骤；接受后 LS 给出跳转 |
| 拒绝（Esc） | ✓ 同上，`reject` |
| 改名后的联动 | ✓ `factor → k` 后预测出后续 `factor` 的修改 |
| 跳转 | ✓ 改类名后给出 Tab Jump |
| 切换文件 | ✓ |
| 有诊断错误时 | ✓ `code_diagnostics` 带上 |
| 复制粘贴后 | ✓ 轨迹出现 `CLIPBOARD` 步骤 |
| 多字节字符 | ✓（用来核对位置单位） |

## 3. 协议要点（给阶段 4 的速查）

```
① api_key ──GetUserJwt──▶ user_jwt（15 分钟）
② POST https://inference-us-west-lb.codeium.com/exa.api_server_pb.ApiServerService/GetTab
   Connect 服务端流，application/connect+proto，请求帧 gzip
   GetTabRequest {
     metadata { api_key, user_jwt, ide_name="windsurf", ide_version, extension_version, ...(其余选填) }
     provider_source = PROVIDER_SOURCE_SUPERCOMPLETE          # 必填
     model = MODEL_TAB_EXPERIMENTAL_4                         # 必填，见问题 14
     language = LANGUAGE_*; streaming_completion_version = 2; prompt_id = uuid
     unified_prompt_components {
       command_intent_info {                                  # 必填：当前文档和光标
         input_document { text, cursor_offset(UTF-8 字节), absolute_uri, workspace_uri, editor_language, line_ending, is_dirty, timestamp }
         selection = 光标行前后各 5 行的原文（去掉首尾空行）; selection_start_line / selection_end_line（0 起，end 不含）
         instruction = 固定句子; request_source = COMMAND_REQUEST_SOURCE_SUPERCOMPLETE }
       cortex_trajectory { trajectory_id=uuid, trajectory_type=SUPERCOMPLETE,
                           parent_references=[{trajectory_id=会话主轨迹 id, type=USER_MAINLINE, step_index=-1}],
                           steps=[...全量轨迹...] }        # 首次 / 缓存失效时
       code_diagnostics, supercomplete_feedback_context      # 选填
     }
     trajectory_steps_v2 { hashes=[服务端上次回传的], steps_after_hashes=[新步骤] }   # 有缓存时代替 steps
   }
③ 响应帧：DeltaSupercomplete{delta_old_str} → PreResponse{cache_info_v2} → 多条 DeltaSupercomplete{delta_new_str} → is_complete / stop_reason → 结束帧
```

参照实现：`lib/tab_request.py`（`TabSession`：轨迹、缓存、JWT 刷新、MissingInformation 重试），`lib/get_tab.py`（命令行）。

## 4. 问题 1–22

### A. 认证与连接

**1. `api_key` 的格式与位置**
- 格式：`devin-session-token$` + 一个 HS256 JWT（只有 `session_id` 声明，**没有 exp**），共 189 字符，长期有效。扩展代码里还认 `sk-ws-01-…`（旧 Windsurf 会话密钥）和 `cog_…` 两种前缀，非这几种前缀的旧 key 会被 `MigrateApiKey` 迁移。
- 本机位置（导入用）：`~/Library/Application Support/Devin/User/globalStorage/state.vscdb`（SQLite），表 `ItemTable`，`key='windsurfAuthStatus'`，值是 JSON，字段 `apiKey`（明文）。`import_key.py` 依次尝试 Devin、Windsurf 的 macOS/Linux 路径。
- 手动获取：Devin 界面里**没有**显示 api_key 的地方。手动填写时可以自己执行（结果别贴到别处）：
  `sqlite3 ~/Library/Application\ Support/Devin/User/globalStorage/state.vscdb "select json_extract(value,'$.apiKey') from ItemTable where key='windsurfAuthStatus'"`
- 验证：`.env` 清空后在 Mac 上执行 `run import-key -y`，再执行 `run get-tab` 能出预测；导入值与手填值一致。

**2. 要不要换短期令牌**
要。每个 `GetTab` 的 metadata 里 **`api_key` 和 `user_jwt` 都得带**：只带 api_key 回 `invalid_argument`，只带 jwt 也是 `invalid_argument`，不带 jwt 回 internal error。
- 换取：`POST https://server.codeium.com/exa.auth_pb.AuthService/GetUserJwt`，一元调用（`application/proto`），请求只有 `metadata`（带 api_key），响应 `user_jwt`。
- 有效期：HS256 JWT，`exp` 为签发后 **15 分钟**（无 iat，按 exp 减去获取时间实测 900 秒）。声明里有套餐、团队等信息。
- 刷新：没有单独的刷新接口，过期前重新调 `GetUserJwt`。`TabSession` 在过期前 60 秒重取。令牌只放内存。

**3. `metadata` 字段**
- 最小可用集合（实测）：`api_key`、`user_jwt`、`ide_name`、`ide_version`、`extension_version`。
- LS 实际填的：`ide_name=windsurf`、`ide_version=3.10.48`、`extension_name=windsurf`、`extension_version=1.48.2`、`extension_path`、`locale`、`os`（LS 填一段 JSON：Os/Arch/Release/…；IDE 填 `mac`）、`hardware`（JSON：核数、内存等）、`session_id`（IDE 进程启动时的 uuid）、`request_id`（自增）、`ls_timestamp`、`device_fingerprint`（sha512，算法见 `identity.py`）、`trigger_id`（每次触发一个 uuid）、`plan_name`、`user_jwt`、`f`。
- `f`：LS 计算的 382 字节十六进制串，含义不明（像是签名或指纹），**去掉后请求照常成功**。
- 校验情况：只确认了 api_key 和 jwt 会被校验；其余字段改动或省略都没有报错。和 `WncFht/devin2api` 文档里对话接口的经验一致：缺必填字段时云端也只回不透明的 internal error，metadata 里的标识类字段静默接受。
- 建议：正式实现照 LS 的样子填全，`f` 不填，值集中定义在一处。

**4. 请求头，有没有防重放**
LS → 云端的头：`User-Agent: connect-go/1.18.1 (go1.26.6)`、`Connect-Protocol-Version: 1`、`Connect-Timeout-Ms`（GetTab 约 9300）、`Content-Type: application/connect+proto`、`Connect-Content-Encoding: gzip`、`Connect-Accept-Encoding: gzip`、`Accept-Encoding: identity`。一元调用用 `application/proto` + `Accept-Encoding: gzip`。**没有签名头和时间戳头**，鉴权全在 body 的 metadata 里。唯一像防重放的是 `metadata.f`，但不是必填。原样重放抓到的请求（换新 jwt）能拿到同样的预测。

**5. 云端地址**
- API：`https://server.codeium.com`（GetUserJwt、GetUserStatus、Ping、ProvideFeedback、分析上报等）。
- 推理：`GetTab` 和 Tab Jump 的 `GetChatMessage` 发到 `https://inference-us-west-lb.codeium.com`。这个地址来自 unleash 开关 `inference-server-url`，按 `requestedModelId` 匹配：`MODEL_TAB_EXPERIMENTAL_4/6/7` 和 `MODEL_CHAT_20706` 对应 `exawest → inference-us-west-lb`；其他模型对应 `southcentral(-lb).codeium.com`、`server.codeium.com` 等变体。
- 实测 `GetTab` 发到 `server.codeium.com` 也能成功（多一跳，首包延迟相近）。`inference.codeium.com` 在当前网络下解析不了。
- 按区域或账号类型是否不同：开关规则里只按模型、IDE、版本、套餐分流，没看到按区域分；企业版有 `portal_url` 等另一套，没有测。建议地址做成可配置，默认 `inference-us-west-lb`。

**6. 心跳 / Ping**
LS 每 30 秒左右向 `server.codeium.com` 发一次 `ApiServerService/Ping`；IDE 每秒向 LS 发一次 `Heartbeat`（只是本地进程保活）。直连实验整个过程中一次 Ping 都没发，`GetTab` 全部正常，**不需要心跳**。

### B. 请求内容

**7. `unified_prompt_components` 实际填了什么**
| 字段 | 官方 LS 是否填 | 内容 / 上限 |
|---|---|---|
| `command_intent_info` | 每次都填，**必填** | `input_document` 是**当前文件全文**（没看到截断；IDE 侧对其他文件有 1 MiB 总量限制）；`selection` 是光标行前后各 5 行的原文：`[row-5, row+6)`，去掉窗口首尾的空行，按文件边界截断（27 个样本都符合；半径来自 unleash `SUPERCOMPLETE_LINE_RADIUS`，变体有 3/5/7/15） |
| `cortex_trajectory` | 每次都填 | 首次和缓存失效时放全量轨迹，否则 `steps` 为空，步骤改放 `trajectory_steps_v2` |
| `chat_messages` | 填一条旧格式的 `code_block_refactor` 意图 | **可省**（去掉后照常出预测） |
| `code_diagnostics` | 有诊断时填 | IDE 侧只取光标所在行 ±10 行内的诊断；开关 `SUPERCOMPLETE_CODE_DIAGNOSTICS_TOP_K=5`，严重级别阈值开关取值 `all_diagnostics` |
| `supercomplete_feedback_context` | 每次填（可能为空） | 最近一次**被接受**的预测：`accepted`、`completion_id`、`timestamp_ms`、`diff_suggestion`（含 character_diff 和 unified_diff） |
| `other_documents` | **不填**（IDE 给 LS 传了，LS 不转发） | — |
| `context_module_result`、`deep_wiki_context*` | 不填 | — |

**8. 当前文档和光标怎么传**
放在 `command_intent_info.input_document`：全文 + `cursor_offset`（**UTF-8 字节偏移**）。选区原文放在 `selection` + `selection_start_line` / `selection_end_line`（0 起，end 不含；取 `[row-5, row+6)`，去掉首尾空行，按文件边界截断）。LS 在预测性请求里还会填 `input_document.cursor_position{row,col}`。**不是**通过 `supercomplete_active_doc` 轨迹步骤传的：官方 LS 不发这个步骤，不过实测云端也接受这种步骤。

**9. 轨迹步骤**
实际出现的步骤类型：
| 类型 | 产生时机 | 内容 |
|---|---|---|
| `CODE_ACTION` | 用户编辑（LSP didChange）；LS 的预测性请求还会把「假设被接受的预测」也当作一步 | `action_spec.command.line_range{uri,start_line,end_line}` + `action_result.edit{absolute_uri, diff{start_line,end_line,unified_diff.lines[{type,text}]}}`；**某个文件在轨迹里的第一步**还带 `original_content`（编辑前全文）。diff 窗口是变更行前 10 行到变更行后若干行，按文件末尾截断。连续输入会合并成一步，触发或 IDE 动作时切分 |
| `SUPERCOMPLETE_FEEDBACK` | 接受或拒绝之后 | `completion_id`、`feedback_type`（`accept` / `reject`）、`feedback_reason`（`intentional`）、`document`（当时全文）、`feedback_delay_ms`、`provider_source` |
| `CLIPBOARD` | 请求里带了剪贴板 | `clipboard.content`（IDE 侧：≤1000 字符、5 秒内复制的、看起来不像密码） |

步骤公共字段：`status=DONE`，`metadata.source=USER_EXPLICIT`，`metadata.created_at`。
- 没观察到：`VIEW_FILE`、`VIEW_CODE_ITEM`、`READ_TERMINAL`、`LINT_DIFF`（开关 `tab-prompt-disabled-step-types=["CORTEX_STEP_TYPE_LINT_DIFF"]` 明确禁用了它）。
- 保留多少步：一个约 70 秒的会话里涨到 17 个哈希，没有观察到裁剪，上限没有测出来。Tab Jump 的提示词按 token 预算截断（`TAB_JUMP_CUMULATIVE_PROMPT_CONFIG` 里有 `trajectory_truncation_multiplier=0.5` 等）。阶段 5 建议自己设上限（例如最近 50 步或 10 分钟）。
- **轨迹为空（一步都没有）时云端回 internal error**。这正是最初 LS 驱动失败的原因：没发 `RefreshContextForIdeAction`，LS 没开始记录编辑。原生实现要保证至少有一步编辑；纯移动光标没有编辑时不发请求。

**10. 哈希怎么算**
**客户端不用算。** 首次请求在 `cortex_trajectory.steps` 里发全量，服务端在 `PreResponse.cache_info_v2.hashes` 里回传每一步的哈希（uint64，一步一个）。下一次请求把这个列表（或它的前缀）原样放进 `trajectory_steps_v2.hashes`，新步骤放进 `steps_after_hashes`，`cortex_trajectory.steps` 留空。哈希值对同样的步骤是稳定的，具体算法不需要知道。编造的哈希会得到 `MissingInformation{start_step:0}`，重发全量即可恢复。

**11. `MissingInformation`**
出现的情况：带了服务端不认识的哈希，或者只发了 `steps_after_hashes` 却没有 `hashes`。返回 `{start_step: 0, uris: []}`（实测 uris 总是空）。处理：清掉本地哈希，把全量轨迹放回 `cortex_trajectory.steps` 重发一次。`TabSession.send` 已实现，再缺就放弃（LS 里也有「received multiple missing information responses」的日志）。

**12. `cache_info_v2` / `uris_to_hashes`；不实现缓存行不行**
- `cache_key` 等于 `parent_references` 里 USER_MAINLINE 的 `trajectory_id`；没有 parent 时等于本请求自己的 `trajectory_id`。所以每个编辑会话要固定一个主轨迹 id。
- `uris_to_hashes` 实测从未出现。
- **每次发全量可行**：所有重放和探针都是全量，都成功，延迟没有明显差别（轨迹几十步时只有几 KB）。阶段 4 可以先发全量，阶段 5 再加哈希缓存，逻辑很简单。

**13. `context_module_result`**
当前版本的 LS 在 `GetTab` 里**不发**检索结果，所有抓包里都没有。检索类上下文只出现在 Tab Jump 的提示词里，形式是文本：文件内容、近期 diff、当前文件带 `<|cursor|>`。所以「自己实现检索」这一项对 Tab 修改预测不是必需的。

**14. `experiment_config` / `model` / `provider_source`**
- `model`：**必填**，`MODEL_TAB_EXPERIMENTAL_4`。来自 unleash `SUPERCOMPLETE_MODEL_CONFIG`（`ide=windsurf` 的规则下发这个值）。不填或填 `MODEL_TAB_BASE_1` 都回 internal error。`_LOW` / `_HIGH` 两个开关还有 `EXPERIMENTAL_5/6/7`、`MODEL_CHAT_23310` 等变体，没有测。
- `provider_source`：**必填**，`PROVIDER_SOURCE_SUPERCOMPLETE`，不填回 `invalid_argument`。
- `experiment_config`：**可省**。LS 发 `SUPERCOMPLETE_MODEL_CONFIG`（json `{"model_name":"MODEL_TAB_EXPERIMENTAL_4"}`）、`API_SERVER_CLIENT_USE_HTTP_2`、`AUTOCOMPLETE_FAST_DEBOUNCE_MS(disabled)`。
- `streaming_completion_version = 2`，`language` 用 `Language` 枚举。
- 取值方式：都是 LS 从 unleash（`https://unleash.codeium.com/api/client/features`，`Unleash-Appname: codeium-language-server`）按 ide / 版本 / 套餐算出来的。原生实现用常量即可，但模型名和推理地址要能在设置里覆盖，官方换模型时不用改代码。

**15. 位置单位**
- 行号：全部从 **0** 开始（`selection_start_line`、DiffBlock 的 `start_line`、`line_range`、`DocumentPosition.row`）。
- `Document.cursor_offset` 和 `selections` 的偏移：**UTF-8 字节**（扩展代码 `numCodeUnitsToNumUtf8Bytes`）。
- `Document.visible_range` 的列：**UTF-16**（直接取 VS Code 的 `character`）。
- 响应里的修改预测**不带位置**：27 次 `GetTab` 响应里 `start_line` / `end_line` / `cursor_position` 都没出现，修改是「把 `delta_old_str` 换成拼起来的 `delta_new_str`」，靠文本定位。Tab Jump 的位置是 `<|cursor|>` 标记在 `TargetContent` 里的位置，也是文本。所以原生实现只需要做一次「字符 → UTF-8 字节」的光标换算。
- LS 返回给 IDE 的 `Diff.cursor_position` / `TabJump.jump_position` 里列的单位没有核实（只影响备选方案，LS 返回的列看起来是按字符计）。

### C. 响应内容

**16. 一次请求几条增量、怎么拼**
帧的顺序固定：
1. 一条 `DeltaSupercomplete{delta_old_str}`：等于 `selection` 原文（不含 `<|cursor|>`），表示要被替换的区域。
2. `PreResponse{request_id, model_features, cache_info_v2}`（`prompt` 字段是空的，服务端不回提示词）。
3. 7–43 条 `DeltaSupercomplete{delta_new_str}`，**按顺序拼接**就是替换后的完整文本。增量之间间隔约 5–20 ms。
4. `is_complete=true` 的帧（最后一段文本可能就在这一帧里），随后一条空的 `is_complete` 帧，再一条带 `stop_reason`（常见 `STOP_REASON_STOP_PATTERN`）的帧，最后是 Connect 结束帧。

每帧都带 `path`（绝对路径，不带 `file://`）。实现时把所有 `delta_old_str`、`delta_new_str` 分别累加到流结束为止。首条增量到完成的间隔中位数约 200 ms，所以默认等完整结果再显示就够了。

**17. `DeltaSupercomplete` 的语义**
`delta_old_str` 是光标附近窗口（`selection` 那几行）的原文，`delta_new_str` 拼起来是这个窗口改写后的全文，可能比原窗口长（会往后补行）。`start_line` / `end_line` / `cursor_position` / `is_import` 在本版本里没有出现。生成编辑时：在文档里定位 `old_str`（就是 selection 那几行），对 old / new 做字符级 diff，得到最小编辑。old == new 表示无预测。LS 对结果还有一层客户端过滤，相关开关 `SUPERCOMPLETE_FILTER_*`：去掉空操作、纯空白、还原上一次编辑等。

**18. `DeltaTabJump` 之后要不要再发请求**
本版本的跳转**不是** `GetTab` 返回的（抓到的 `GetTab` 响应里一次 `DeltaTabJump` 都没有），而是 LS 每次触发时并行发出一个 `GetChatMessage`：
- `provider_source=PROVIDER_SOURCE_TAB_JUMP`，`internal_chat_model=MODEL_CHAT_20706`，`request_type=COMMAND`，`configuration{max_tokens 2048, temperature 0.1, top_k 50, stop_patterns…, last_message_is_partial}`；
- 提示词**由 LS 在本地拼好**：一段固定的系统提示，加若干条 `chat_message_prompts`（「USER 打开了文件 X 第 a–b 行」+ 文件内容，若干条 `[diff_block_start]…[diff_block_end]` 编辑记录，`<additional_metadata>` 里的当前文件全文带 `<|cursor|>`，再加 `<user_request>`），最后一条是 SYSTEM 角色的半截 `<replace_file_content>{ "TargetFile": …, "ReplacementChunks": [{ "TargetContent":`，让模型续写。完整样例在 `.scratch/tabjump_example.txt`（不提交）。
- 模型续写出 `TargetContent`（用 `<|cursor|>` 标出跳转点）和 `ReplacementContent`（跳过去之后要做的修改）。
- 跳转后**不必立即再请求**：`ReplacementContent` 就是跳过去之后的修改预测。LS 在接受跳转后会以 `TAB_JUMP_ACCEPT` 触发下一次请求；开关 `TAB_JUMP_AS_CACHED_SUPERCOMPLETE` 在稳定版上没开，所以稳定版是重新请求一次 `GetTab`。
- 不经 LS 直接重放这个 `GetChatMessage`（换新 jwt）能拿到同样的结果。

**19. 跨文件**
`DeltaTab.path` 是绝对路径，Tab Jump 的 `TargetFile` 也是绝对路径，所以协议上可以跨文件。抓包里没有出现跨文件的预测：测试工作区很小，Tab Jump 提示词也只拼了当前文件。阶段 4 先按同文件实现，`path` 和当前 buffer 不一致时走 `EditPrediction::Jump`。

**20. 延迟**（每组 22 次，串行、间隔 2.5 秒；在容器里经同一网络出口测得）
| 组 | 首条增量 P50 / P90 | 完成 P50 / P90 |
|---|---|---|
| 直连云端（`run latency direct`，带哈希缓存） | 374 / 392 ms | 559 / 707 ms |
| 经过 LS，每次输入预测不到的内容（`run latency ls-diverge`） | 拿不到（LS 对 IDE 是一元调用，只能看完成） | 682 / 915 ms |
| 经过 LS，输入沿着上一条预测走（`run latency ls`） | — | 1–5 ms（22 次里 21 次命中 LS 的本地预测缓存，只有第 1 次 1478 ms） |

结论：网络和推理本身直连更快（少一跳，LS 内部还要拼两个请求）。但官方体验的关键在 LS 的**预测性预取**：每次出预测后，LS 立刻假设它被接受，再发一次 `GetTab`（触发条件 `SUPERCOMPLETE_PREDICTIVE`，每个触发对应 1–3 个 `GetTab` 和同样多的 `GetChatMessage`）；用户照着输入时直接从本地缓存给出结果（「typing as suggested」）。原生实现要达到同样的手感，阶段 5 得做这两样：沿预测输入时本地裁剪当前预测，以及预测性预取。

### D. 反馈与副作用

**21. 接受和拒绝**
- IDE → LS：`ProvideCompletionFeedback{completion_id, prompt_id, is_accepted, source=SUPERCOMPLETE, document, feedback_delay_ms, is_intentional_reject, completion_text…}`。
- LS → 云端：`POST server.codeium.com/exa.api_server_pb.ApiServerService/ProvideFeedback`，内容 `{prompt_id, completion_id, source=COMPLETION_SOURCE_NETWORK, feedback=FEEDBACK_TYPE_ACCEPT|REJECT, extra_info=FEEDBACK_EXTRA_INFO_INTENTIONAL_REJECT（Esc）, timestamp_unix_ms, feedback_delay_ms, provider_source}`。
- 同时进入下一次请求：轨迹里加一个 `SUPERCOMPLETE_FEEDBACK` 步骤；接受的预测还会写进 `supercomplete_feedback_context.feedback`。
- 不调 `ProvideFeedback`，`GetTab` 照常工作（所有直连实验都没发）。建议阶段 5 只做「进入轨迹」这部分；`ProvideFeedback` 是一个很轻的一元调用，为了和官方客户端的流量形态一致，也可以发。

**22. 分析类上报**
一个约 70 秒的抓包会话里，LS → 云端的调用次数：`RecordCortexTrajectoryStep` 82、`RecordCortexTrajectory` 58、`RecordContextToPrompt` 54、`RecordCommandUsage` 46、`RecordCompletions` 46、`RecordTabTrajectoryStep` 45、`ProvideFeedback` 2、`RecordCodeTrackerUpdates`（每 30 秒）、`Ping`（每 30 秒）、`GetUserStatus` 3、`RecordStateInitializationData` 1、`RecordAnalyticsEvent` 1，还有 unleash 的 `features`（每 60 秒）、`register`、`metrics`。
直连时这些一个都没发，所有 `GetTab` 和 `GetChatMessage` 都正常，**没有可见影响**。风险：长期只发 `GetTab`、不发任何上报的流量形态和官方客户端差别很大，如果服务端拿这个做风控，有被识别的可能。没办法验证，见第 7 节。

## 6. 缺口与绕过办法

| 缺口 | 影响 | 绕过 / 安排 |
|---|---|---|
| Tab Jump 要自己拼提示词（`GetChatMessage` + 固定模板） | 跳转预测要多做一块 | 模板、模型、参数都抓到了，直连重放可用。阶段 4 先只做 `GetTab` 修改预测，跳转放到阶段 5，按抓到的模板实现 |
| 预测性预取、沿预测输入的本地缓存 | 不做的话手感比官方慢（官方大多数按键 1–5 ms，直连每次约 560 ms） | 阶段 5 实现。逻辑清楚：出预测后假设接受、再请求一次；用户输入的字符和预测前缀一致时本地裁剪 |
| 模型名、推理地址来自 unleash | 官方换模型以后，硬编码的值可能失效 | 设置里可以覆盖；报错时提示检查。可选：启动时拉一次 unleash features（又多一类请求，暂不做） |
| `metadata.f` 含义不明 | 现在不是必填，以后可能变成必填 | 不填。哪天 GetTab 开始拒绝，再回来看 LS 怎么算（备选：桥接 LS） |
| 不发分析上报 | 可能被风控识别 | 无法验证。至少发 `ProvideFeedback`；必要时补发低频的 `Ping` |
| 打开文件不编辑时 LS 发空轨迹被拒 | 官方 LS 在这种情况下也拿不到预测 | 原生实现在没有编辑步骤时不发请求 |
| Mac 版 LS → 云端没抓到 | 只抓了 Linux 版（同一提交、同样的 proto） | 不影响结论；真想核对见第 8 节 |

## 7. 封号风险与本次的请求量

本次直连云端（不含 LS 自己发的）：`GetTab` 约 60 次、`GetChatMessage` 1 次、`GetUserJwt` 约 20 次，全部串行，间隔 ≥2 秒，比一个人正常打字时官方客户端的请求频率低（官方每次触发 1–3 个 GetTab + 1–3 个 GetChatMessage）。请求头对齐 connect-go，metadata 对齐官方取值。期间没有出现限流或认证异常。

## 8. 需要用户手动做的事

完成本阶段的结论**不需要**用户手动操作。下面是可选项：
1. 如果想拿 Devin.app 本身（而不是脚本驱动的 LS）的真实流量做最终核对，只有两条路，都需要你来决定：
   - 在 Mac 登录钥匙串里临时信任一个自签 CA（属于全局改动，事后要删掉），然后用 mitmproxy 之类的工具抓 Devin.app；
   - 或者在容器里开 sshd，让 Devin 用 Remote-SSH 连进容器，LS 就会在容器里运行，可以复用 `mitm.py`。之后在 Devin 里打几行字即可。
2. 在 Devin 里**不要退出登录**：退出后 `devin-session-token` 可能失效，到时重新执行 `run import-key`。

## 10. 决定

**走原生方案：阶段 4、5。**

依据：
- 用完全自己构造的请求（自己的文档、自己的编辑轨迹）直连云端，拿到了合理的修改预测，包括改名联动和补全。
- 认证弄清了：api_key → `GetUserJwt` → 15 分钟的 jwt，两者都放进 metadata。没有签名、没有防重放头。
- 哈希不需要客户端计算：服务端回传、客户端原样带回；每次发全量也可行。
- 必填字段、模型、地址、位置单位、响应拼接规则都弄清了。
- 剩下的缺口（Tab Jump 的本地提示词、预测性预取）都有抓包样本，可以直连复现，属于工作量问题，不是可行性问题。

对后续文档的调整：
- 阶段 4 的「上下文本阶段提供三类」改为：当前文档 + 窗口（`command_intent_info`）、编辑步骤、诊断。**去掉** `other_documents`（官方不发）。
- 阶段 4 的跳转预测改为「阶段 5 做」，或者在阶段 4 末尾单独做一项，实现方式按问题 18：`GetChatMessage` 加本地模板。
- 阶段 5 去掉「自己实现检索」（`context_module_result` 官方不发），增加「预测性预取」和「沿预测输入的本地缓存」。
- 备选方案（阶段 8）补充：LS 需要先收到 `RefreshContextForIdeAction`（STARTUP、ACTIVE_EDITOR_CHANGED、SELECTION_CHANGED）才会开始记录编辑；云端报错时 LS 对 `HandleStreamingTabV2` 不响应，桥接要自己设超时。
